## Context

本变更以当前 `documents/产品需求文档.md` 为产品基线。四份目标文档主要覆盖日志业务：顶层设计缺任务模块与关系；接口文档缺任务契约；技术设计缺任务存储、流程与页面设计；计划缺 US-30 至 US-41 的交付与测试安排。现有 Flutter、React、Spring Boot、MyBatis、PostgreSQL 技术栈不变。

## Goals / Non-Goals

**Goals:**
- 同步顶层、接口、技术、里程碑四份文档，保证字段、状态、权限、页面来源和验收口径一致。
- 保留日志、点评、日志统计、管理员只读日志权限及截止处理的既有规则。
- 让每项新增需求具有可实现的设计、可测试的接口契约、负责人和交付阶段。

**Non-Goals:**
- 不修改产品需求、不实现代码、DDL 迁移或运行时 API，不更新根目录 `tasks.md`。
- 不实现通知推送、AI、离线、导出或生产部署增强，不替代或勾选 `backend-api-contract-and-workplan` 的任务。

## Decisions

### 1. 按文档职责同步，而非只追加统一补丁章节

顶层设计更新模块、数据模型、权限、流程、接口概要和分工；接口文档补充端点、DTO、枚举、错误与权限示例；技术设计补充 ER/DDL、索引、事务/条件更新、状态机、客户端路由及测试；项目计划更新里程碑概览、交付明细、Sprint 概览与逐项任务。只在末尾追加说明会使原“范围”及主表继续遗漏任务，因此须同步相关原章节，保留既有日志内容。

### 2. 共享任务与接收人执行记录分离

设计采用 `tasks` 存储派发人及名称、详情、开始日期、截止日期、紧急程度，`task_assignments` 存储接收人、执行状态和检查状态，使用任务/接收人唯一约束。检查邀约与结果记录关联接收记录，便于保留退回历史。不得将状态放在共享任务行导致一人操作影响所有接收人。日期使用 DATE，校验截止日不早于开始日。

权限独立于日志数据范围：只能沿创始人→部门老总→团队长→员工的直接组织关系派发；派发人编辑内容和执行检查，被派发人只更新本人执行进度。管理员日志全局读取权限不扩展为个人任务读取权限。每次写操作均须服务端校验对象所有权及当前状态。

### 3. 执行状态与检查结果区分表达

执行状态为未开始、进行中、已完成；完成后发起邀约进入待检查，派发人给出通过或退回。退回保留检查结果记录，同时执行状态回到进行中，可再次完成并邀约。技术设计与接口契约须给出完整枚举、允许转换、非法转换响应和并发条件；页面显示状态从这些字段推导，避免把“退回修改”同时当永久执行状态。检查不是派发人代改执行进度，也不依赖消息推送。

### 4. 自建任务与公司展示内容分离

自建任务采用独立个人记录，只含名称、详情、执行状态及必要的内部标识/审计信息，不暴露日期、紧急程度或派发检查字段；仅本人可见和编辑。“个人十大工作任务”是同一份自建数据的入口，不创建第二份数据。公司两类内容采用独立展示模型，管理员在 Web 维护重要事项，创始人在 Android 维护重要任务，其他用户只读；不复用 `tasks` 表或计入任务统计、日历、数据地图。

不因“十大”名称额外推导全量任务硬上限；实施时以当前产品正文明确约束为准，不根据旧摘要补写限制。

### 5. 页面复用领域接口，聚合读模型不提供写入口

导图页按 2×2 显示公司事项、公司任务、个人任务、个人日志，个人区域双击原地编辑，日志仍受草稿/截止校验。个人面板布局为日志、个人任务、任务分发、任务接收，分发入口按权限控制。数据地图聚合本人接收记录和自建任务，空日期/紧急程度返回 null 并显示留空，只读；不聚合本人派发给他人的任务。

日历默认手机当前月，可切换月/周/日，周为 7 天，日视图白底。日历读取本人接收的有日期派发任务及权限允许的日志；日期相交查询覆盖开始/截止日，任务绿优先于日志红，不以颜色表示状态或紧急程度。自建任务和公司展示内容排除。客户端刷新/缓存失效须让来源页修改反映到导图与地图。

### 6. 契约与排期保持单一基线

详细 REST 契约以 `后端接口文档.md` 为准，技术设计采用相同路径、字段、错误码与权限码，顶层仅摘要引用。延续 `/api`、统一响应、分页和 Asia/Shanghai 业务日期约定；手机当前日仅用于日历初始导航，不能覆盖日志服务端业务日期。

保留 2026-09-18 至 2027-01-07、16 Sprint、M1–M9 的原计划日期。将新增任务设计/契约、后端与数据库、Android 页面、Web 事项管理、联调和测试纳入对应阶段，并注明新增范围带来的容量风险与待复核工作量。这是更新计划基线，不声明历史任务已完成；不擅自顺延日期或删除日志交付。

## Risks / Trade-offs

- [多人状态串改] → 接收记录唯一约束、对象级鉴权、条件更新和双接收人反例测试。
- [两份接口说明漂移] → 同步端点与字段并交叉核对，不以摘要代替详细契约。
- [排期容量不足] → 显式标记新增工作量与依赖，不在未获批准时更改里程碑日期。
- [组织变更、任务删除/撤销、完成后改内容等尚无产品规则] → 不擅自新增业务流程，记录为后续实施前确认点；当前文档只承诺已确定行为。
- [原日志规则被任务状态覆盖] → 对照原文检查日志章节与 US-01 至 US-29，保留截止、点评隐私与统计口径。

## Migration Plan

1. 先建立需求到四份文档章节及 US-30 至 US-41 的对应清单。
2. 按顶层设计→接口契约→技术细化→计划更新顺序修改并逐项核对。
3. 进行术语、路径、枚举、权限、日期与日志保留回归审阅。
4. 本次无部署和数据库迁移；回退仅针对本变更四份文档的新增/调整差异，不覆盖用户其他编辑。

## Open Questions
