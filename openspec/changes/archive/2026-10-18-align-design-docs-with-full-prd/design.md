## Context

`documents/产品需求文档.md` 是本次对齐的产品基线。上一轮变更已把任务派发、逐接收人检查、自建任务、公司展示内容和四个页面的主要行为写入四份文档及 OpenSpec 主规格；本轮全量审计只处理仍未被四份文档一致表达的残余条款。已确认无需重复处理的内容包括：任务与接收记录分离、状态枚举、点评隐私、数据地图空值与 31 天日历范围、离线容错，以及组织负责人唯一索引。

残余偏差集中在四类：组织与身份约束、账号开通方式、页面呈现细节、质量与排期验证。技术栈、总体架构和既有日志规则不变。

## Goals / Non-Goals

**Goals:**

- 让 PRD 中的组织唯一性、角色归属、账号开通、页面细节、性能与易用性指标在顶层、接口、技术和计划四份文档中有一致、可执行、可验收的表述。
- 消除顶层设计 Sprint 规划与项目计划 16 Sprint/M1–M9 的明确冲突。
- 为后续 apply 提供逐文档、逐章节的核对清单，避免再次出现“主规格已覆盖、配套文档仍缺失”的情况。

**Non-Goals:**

- 不修改 `documents/产品需求文档.md`，不改变任何已确认的产品行为。
- 不实现后端、Flutter、React 代码，不执行 DDL 迁移，不新增接口实现。
- 不重新设计任务模型、日志规则、点评隐私、数据地图或日历算法。
- 不调整 2026-09-18 至 2027-01-07 的项目起止日期，不删除既有日志与任务交付项。

## Decisions

### 1. 以 PRD 条款为锚点，做最小差异修改

每项修改必须能对应到 PRD 的明确条款：4.1、4.2、4.3、5.3、6.1、6.8.2、6.8.3、9.2、9.3。只在四份文档的对应章节补充或纠正，不重写已对齐章节，也不在文档末尾追加与正文脱节的补丁章节。

### 2. 组织唯一性分三层表达

- 组织层：`companies.founder_id`、`departments.manager_id`、`teams.leader_id` 各自使用部分唯一索引，保证至多一名负责人；现有技术设计 §6.3.6 已具备，保留并明确其对应 PRD 4.1。
- 用户层：`users` 增加角色-归属 CHECK，约束员工/团队长必须同时有部门与团队、部门老总必须有部门且无团队、创始人和管理员两者均为空。
- 服务层：团队长的 `team_id` 必须等于其作为 `teams.leader_id` 的团队，且该团队的部门必须等于用户的 `department_id`；这是跨表约束，不能只靠 CHECK，必须在用户创建/编辑与团队负责人设置时校验。

接口文档与技术设计使用同一套规则和同一个冲突错误码，避免两份契约漂移。

### 3. 账号只由管理员开通

PRD 6.1 明确管理员在 Web 端创建所有账号且不支持自助注册。顶层设计在管理员权限中写明，接口文档在认证章节明确不存在注册端点，技术设计在认证接口与权限设计中保持只读说明。登录、停用/启用、锁定行为不变。

### 4. 页面细节写入顶层设计的页面数据来源章节

顶层设计 §7.5 需要补齐四项可直接验收的细节：视图页左上角提供日/周/月选择按钮；日视图白色背景；日历日期范围包含开始日和截止日；个人面板四板块按左上日志、右上个人任务、左下任务分发、右下任务接收排列。这些细节已在 `task-presentation` 主规格和 PRD 中存在，本次只修正顶层文档缺失，不改变业务规则。

### 5. 排期只保留一个基线

顶层设计 §10.1 删除 Sprint 0/1/2/3/Final 的旧划分，改为与 `项目计划与里程碑.md` 一致的 Sprint 1–16、M1–M9、2026-09-18 至 2027-01-07。顶层只保留概览，逐 Sprint 任务以项目计划为准，避免两份排期再次分叉。

### 6. 质量指标与测试安排同步落地

性能章节补充“关键接口成功率不低于 99%”；易用性章节补充“新用户 3 分钟内完成第一条日志提交”“常用 Android 分辨率下页面正常显示”，并保留错误提示说明修复方式、主要操作 ≤ 3 层。测试设计增加易用性测试行；项目计划 M8 交付物与 Sprint 15 任务增加易用性测试，Sprint 3 与 Sprint 12 增加组织唯一性和角色-归属校验测试。

## Risks / Trade-offs

- [CHECK 约束过严影响后续角色调整] → 角色-归属规则集中在服务层校验函数与单一 CHECK 中，未来调整角色时同步修改两处并补迁移说明；本期不执行迁移。
- [团队长一致性无法用单表 CHECK 表达] → 明确由服务层在创建/编辑用户和设置团队负责人时校验，并用集成测试覆盖跨表不一致场景。
- [顶层 Sprint 概览与项目计划再次漂移] → 顶层只保留 16 Sprint 概览并注明详细任务以项目计划为准，验收时交叉核对 Sprint 数量、里程碑和起止日期。
- [易用性指标难以自动化] → 采用手工走查 + 真实 Android 设备测试，并在 M8 交付物中要求形成测试记录；具体机型矩阵作为测试配置，不扩展为产品需求。
- [文档修改误伤已对齐内容] → 按章节最小修改，完成后对照 PRD 4.1–4.3、5.3、6.1、6.8.2–6.8.3、9.2–9.3 与既有日志/任务条款做回归审阅。

## Migration Plan

1. 先核对 PRD 锚点与四份文档现有章节，确认每项偏差的唯一落点。
2. 按顶层设计 → 后端接口 → 技术设计 → 项目计划的顺序修改，保持术语、错误码和日期一致。
3. 运行 `openspec validate "align-design-docs-with-full-prd" --strict`，并交叉核对四份文档中的组织规则、页面细节、质量指标和排期。
4. 本次无代码与数据库迁移；回退仅涉及本变更写入的文档差异，不覆盖用户其他编辑。
