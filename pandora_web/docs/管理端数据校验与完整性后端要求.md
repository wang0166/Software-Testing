# 管理端数据校验与完整性后端要求

本文供后端同学实现、迁移和联调验收。现有接口见[后端接口文档](../../documents/后端接口文档.md)。下文列出本轮待交付的变更。前端已接入身份证号编辑、输入校验、重复预查和事件数量预查。数据库写入、跨客户端并发和直接请求的约束由服务端验收。

## 1. 用户资料与唯一性

| 字段 | 写入规则 | 唯一范围与比较规则 |
| --- | --- | --- |
| 账户名 | 开户必填。去两端空白后为 3～20 位小写英文字母、数字或下划线。现有账号名只读 | 全局唯一。存量大小写变体在迁移前按去空白并转小写预查 |
| 手机号 | 开户必填。去两端空白后为以 1 开头的 11 位数字。现有手机号只读 | 全局唯一。旧账号空值可并存 |
| 身份证号 | 开户必填，编辑支持更正。去两端空白，末位小写 x 转大写。校验 18 位结构、实际出生日期、日期不晚于北京时间当天和校验位 | 全局唯一。大小写 x 视为同一个号码。旧账号空值可并存 |
| 姓名 | 去两端空白后必填，最多 64 个字符，须包含文字，拒绝控制字符。保留合法空格、中点和连字符 | 允许同名 |
| 性别 | 开户可空，有值限男或女。现有编辑接口只读 | 无唯一性要求 |

- 手机号和身份证号的唯一性覆盖启用、锁定和停用账号。分别按字段比较，账户名与手机号可以使用同一字符串，例如开户时以手机号作为账户名。
- 手机号由历史约定的可复用改为唯一。先查存量冲突再启用约束。开户与编辑在事务内校验，数据库唯一约束须覆盖全部写入入口。编辑时排除当前用户，允许提交自己的原号码。
- `POST /api/users` 成功返回新用户编号。请求与响应使用现有 `{code,message,data}` 结构。账号冲突沿用 HTTP 409 和 `40906`。

### 身份证号更新契约

- `PUT /api/users/{id}` 在 `realName`、`role`、`departmentId`、`teamId` 之外增加可选 `idNumber`。字段省略时保留原号。传入时必须是非空字符串，显式 `null`、空串及格式非法均返回 HTTP 400。本次没有清除身份证号的业务操作。
- 验证、查重和其他用户字段写入在同一事务内执行。任何字段失败时整次写入回滚。复用 `user:manage` 权限与现有会话撤销规则。
- 成功后 `GET /api/users/{id}` 应向有权限的管理员返回同一用户已保存的规范化身份证号。前端以该读取结果确认修改。修改当前登录管理员后会话被撤销时，用新会话从详情回查。
- 手机号、身份证号冲突返回 HTTP 409，建议使用结构化 `data.field` 分别传 `phone` 或 `idNumber`。如果沿用 `40909`，由 `data.field` 明确冲突字段。参数校验失败建议同样返回字段。提示只说明哪个字段已被使用，避免附带原值、其他人姓名、账号或证件信息。
- 编辑请求继续拒绝未声明字段。身份证号只在授权用户资料接口传输。访问日志、审计字段变化、导出、异常报文和联调日志均按敏感字段处理。审计可记录「身份证号已变更」和操作人、目标用户编号。

## 2. 部门、团队和角色归属

- 部门名称在同一公司内唯一，团队名称在同一部门内唯一。不同部门可各自有「运营组」，筛选、调岗和查询始终按稳定 ID。组织介绍允许相同。
- 名称比较键按顺序执行 Unicode NFKC、去两端空白、将连续空白折叠成一个空格，再做与语言环境无关的小写转换。`QA  2组` 和 `ｑａ　２组` 在同一部门冲突。展示使用填写并去两端空白后的名称。创建、重命名或移动归属时复用同一比较键和唯一约束。
- 名称必填，最多 100 个字符，至少一个 Unicode 字母，包含中文的名称符合该规则。拒绝纯数字、纯符号和控制字符。介绍最多 500 个字符，可留空，有值时至少一个 Unicode 字母。保留正常多行介绍。`研发2组`、`QA-2` 是合法名称。
- `POST /api/departments` 校验公司存在，`POST /api/teams` 校验部门存在，成功返回新编号。现有数据库约束按原始名称比较，需要对规范化后的键补约束。同级重名和并发写入引发的重名都返回 HTTP 409 / `40907`。
- 组员、组长必须属于同一个真实的部门和团队关系，部门负责人只属于部门，系统管理员和创始人无团队与部门归属。团队所属部门、负责人角色、用户所属部门的变更应在同一事务中保持一致。
- 每个公司一名创始人，每个部门一名负责人，每个团队一名组长。保持重复负责人 `40905`、有关联的删除 `40904`、最后可用管理员 `40908`。并发调岗、删除和停用也要保住这些约束。
- 部门列表提供 `managerId`，缺位返回 `null`。对应 `GET /api/users/{id}` 返回真实姓名、角色和归属，供「查看介绍」核对。团队列表沿用 `leaderId` 与 `departmentId`。

## 3. 事件纪和密码

- `POST /api/company-matters` 以实际总量为准，最多保存 10 条。数量检查和插入处于同一受并发控制的事务。已有 9 条时同时新增两个事件，只能有一个请求成功，超额返回明确的 HTTP 409 业务错误。满额可编辑，历史记录可继续分页。存量超过 10 条时停新增，由负责人决定存量处理。
- 标题和备注去两端空白后必填，标题最多 200 个字符，备注最多 100000 个字符。排序为有效的 32 位整数。开始和截止都必须是北京时间 `+08:00` 整点，截止不得早于开始。兼容历史时间为空或只返回日期的读取。
- 管理员开户、重置密码与前端采用一致规则，至少 12 个字符，含大小写英文字母、数字和符号，UTF-8 最多 72 字节，拒绝控制字符。按原值做 BCrypt 哈希，成功后按现有规则撤销旧会话。旧密码仍走现有登录验证。
- 写入请求独立鉴权和校验。认证失败、权限不足、字段非法、重复和写入失败分别返回对应错误。成功前完整提交事务，失败时避免留下部分更新或失配的角色归属。

## 4. 上线前补查

| 风险 | 交付要求 |
| --- | --- |
| 存量值会撞新的唯一约束 | 先查规范化重复和非法历史格式，使用汇总和受控编号提供核对依据，确认归属后用新版本迁移。保留历史空资料。复核备份与恢复，避免自动覆盖、合并或删除 |
| 两位管理员编辑同一用户 | 建议给关键更新加入版本号或 ETag，过期写入返回冲突并刷新，避免覆盖其他管理员刚改的身份证号或归属 |
| 网络超时导致不知道是否已写入 | 写入失败反馈区分业务拒绝与结果未知。建议为高风险创建操作支持幂等标识，超时先回查，避免把重试当作第二次创建 |
| 全量用户列表用于查重会放大敏感数据访问 | 持久化约束负责最终查重。可另提供仅管理员使用的精确查重能力，仅返回冲突字段，编辑时排除当前用户。敏感值走受控 HTTPS 请求体，避免在 URL 中使用身份证号和手机号 |
| 启停、删除、重置与审计 | 验证最后管理员保护、删除关联拦截、旧会话撤销和审计一致性。审计保留动作、操作者、对象编号、时间和结果，剔除敏感原文 |

## 5. 联调验收用例

在隔离 PostgreSQL 运行，使用虚构资料。每个拒绝用例要回查数据库或查询接口，确认之前的记录和关系完整。

1. 旧客户端仅编辑姓名或归属，未发送 `idNumber`，原号码继续可查。编辑空历史记录填写合法号码，刷新详情可查新号码。重新提交当前用户的同一个号码也能成功。
2. 身份证号格式错、出生日期不存在、校验位错和显式空值均拒绝。错误请求同时修改姓名时，姓名也不得落库。
3. 另一个账号使用同一个手机号或身份证号，含停用账号以及身份证末位 `x/X` 变体，分别返回对应字段的 409。两个管理员并发开户或编辑为同一号码，数据库最终只有一条占用。
4. 同名用户能分别开户。大小写或全半角、空白变体导致的同级组织重名会冲突，不同部门的同名团队可按 ID 各自查询。纯数字或纯符号名称、介绍在直接请求 API 时也被拒绝。
5. 并发调岗、分配负责人或删除组织后不会产生冲突岗位、失配归属或零可用管理员。部门介绍中的负责人刷新后与数据库一致。
6. 已有 9 个事件时并发新增，最终为 10 个。第 10 条可刷新回查，满额编辑成功。非法排序、非整点及倒序时间均被 API 拒绝。
7. 弱密码、超 72 UTF-8 字节及无权限请求均失败。成功重置后旧密码及旧会话失效，新密码可登录。检查应用日志、审计、错误响应和联调报告中的敏感字段已脱敏。
8. 模拟具有冲突和空值的旧库，核对迁移能准确预警。对已完成冲突处理的库启用新约束，回查既有用户和组织未发生意外变化。
