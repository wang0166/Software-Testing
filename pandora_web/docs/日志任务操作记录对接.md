# 日志与任务操作记录：前端、后端与移动端对接

## 交接结论与分工

本次交接只覆盖管理员前端需要的工作日志、派发任务操作记录。老师确认：手机端所有角色对日志和任务的新增、修改、删除等操作需要留痕，日志不可删除，任务应支持删除。管理员页面已排除自建任务及其他管理记录。

| 负责方 | 需要完成的工作 | 本次交付边界 |
| --- | --- | --- |
| Web 前端 | 日志/派发任务筛选、操作者/动作/结果/日期查询、分页、只读详情与字段变化 | 已实现；默认及重置查询日志，正式构建不使用演示数据 |
| 后端 | 按实际业务操作保存审计，提供管理员分页/详情查询，补齐任务删除及权限校验 | 由后端同学核对其分支和部署版本，缺失项按下列清单完成 |
| 移动端 | 现有写操作调用真实业务接口，接入任务删除入口并正确处理结果 | 由移动端同学接入；不增加日志删除入口 |

前端完成不代表后端已部署或手机端已联调。任务删除及其实际成功记录尚不能依据本次前端交付标记完成。既有数据需要保留，必要的结构变更由后端同学安排兼容迁移。

## 后端修改清单

1. **覆盖各角色的真实写操作。** 从登录身份取得操作人，日志使用 `LOG`、派发任务使用 `TASK`，不能只记录管理员。按权限生效的日志新增、草稿修改、提交，以及任务派发、执行进度和检查状态变化，应关联到对应日志/任务编号。
2. **由服务端保存记录。** 成功的业务变更与审计写入保持事务一致；移动端不另发“新增审计”请求，也不能指定自己以外的操作人。只读查询不生成增删改记录。服务端若保存失败尝试，应标记失败，不能冒充成功变更。
3. **补齐派发任务删除。** 当前前端不调用删除接口，后端与移动端需共同确定并接入业务接口。建议采用 `DELETE /api/tasks/{taskId}`，其中 `taskId` 为派发任务编号，不是某个接收人的 `assignmentId`；这是待双方确认的接口约定，不表示现有服务已实现。成功响应沿用统一封装；无权限、状态不允许、任务不存在等情况返回明确错误，移动端不能自行当作成功。
4. **删除后仍可追溯。** 删除成功时保留操作人、时间、任务编号、动作、结果及必要摘要；任务消失后，管理员仍能查询该条审计及详情。任务与接收记录等关联数据需一致处理，不能连带删除审计。具体采用逻辑删除还是其他方式由后端确定，本轮不要求恢复接口。
5. **不开放日志删除。** 保留既有日志草稿修改、本人归属和截止限制，不因增加审计而允许修改已提交日志。任务内容编辑若原本没有入口或接口，本交接不要求额外新增；现有进度、检查等修改需要记录，今后新增写操作同样接入审计。
6. **完成管理员查询契约。** 实现或核对下文的列表、详情及筛选；`objectType` 必须由服务端执行，分页和 `total` 使用筛选后的数据。查询只对有权限的管理员开放，不能依靠 Web 隐藏入口实现权限控制。
7. **限制记录内容。** 操作人建议保留姓名与账号快照，账号后续停用或变更后仍可识别。摘要和字段变化不保存密码、令牌、完整身份证号或日志正文；正文只记录发生修改的标记。

动作文字可沿用“新增日志”“修改日志”“提交日志”“派发任务”“更新任务进度”“删除任务”等。`action` 直接展示服务端文字，查询按关键词匹配，不要求手机端传入动作名称。

## 移动端修改清单

1. **使用真实接口模式。** 接到与管理员 Web 相同的业务后端；演示数据、本机草稿缓存的清除不等于服务器日志/任务的新增或删除，不能作为审计联调证据。
2. **沿用现有日志和任务写接口。** 保存草稿、修改草稿、提交日志、派发任务、更新进度及检查等操作由业务接口完成，审计由后端写入。覆盖实际使用这些功能的各角色，不只测试管理员或普通员工其中一种。
3. **接入派发任务删除。** 与后端确定接口及可删除条件后，在有权限且状态允许的任务上提供入口；先确认，再调用接口。后端明确成功后刷新列表；失败时保留原记录并显示原因，不能只从本机列表移除。删除操作发送任务编号，不能误把接收记录编号当任务编号。
4. **不增加日志删除入口。** 管理员 Web 已移除自建任务查询；本次交接不要求恢复移动端的自建任务入口，也不要求修改其他移动端功能。
5. **完成真实链路联调。** 使用不同角色执行实际操作，再由管理员在 Web 查询对应人、类型、时间和详情；特别验证任务删除后仍能打开其操作记录。

## 实施前需双方确定的事项

| 待定事项 | 建议及约束 |
| --- | --- |
| 谁可以删除派发任务 | 建议由原派发人操作，接收人不能删除别人派给自己的任务；这只是建议，尚未作为已确认权限规则 |
| 哪些任务状态可删除 | 未开始、执行中、待检查、已完成等状态是否允许删除，需后端和移动端统一；不能各自判断一套规则 |
| 删除接口与返回格式 | 优先讨论上文建议的 `DELETE /api/tasks/{taskId}`；最终由双方确认，Web 不依赖具体删除路由 |

上述待定项不影响前端只读查询的实现，但会影响任务删除功能的正确性。日志禁止删除、页面仅查 `LOG/TASK` 已明确，不属于待定事项。数据恢复暂不做，直接执行 SQL 的数据库审计不在此次需求内。

## 功能边界

- 管理员在 Web `/audits` 查询手机端各角色对日志、任务的新增和修改记录，以及任务删除记录。日志不开放删除。
- 页面只包含工作日志、派发任务，不提供自建任务、员工账号、组织、公司事项、密码申请或本地维护等其他记录入口。
- Web 只提供查询、筛选、分页和详情，不执行日志或任务的新增、修改、删除，也不提供数据恢复。
- 记录生成、完整性、权限和任务删除规则由后端负责；手机端负责业务操作入口。前端展示接口实际返回的记录，不根据按钮点击自行生成真实审计。
- 当前前端代码可以展示任务删除记录；接口返回及手机端接入仍须对应同学完成并联调。这不表示服务器已经支持任务删除。

## 查询接口

沿用统一 `/api` 前缀、Bearer 认证及 `{code,message,data}` 响应。

`GET /api/audits`

| 查询参数 | 含义 |
| --- | --- |
| `page`、`size` | 从 1 开始的页码、每页条数；页面每页 10 条 |
| `actor` | 操作者姓名或账号，可查询所有角色，不只管理员 |
| `action` | 动作关键词，如新增、修改、派发、提交、删除 |
| `objectType` | 单个业务类型；只允许 `LOG` 工作日志、`TASK` 派发任务 |
| `result` | `SUCCESS` 或 `FAILED` |
| `from`、`to` | `YYYY-MM-DD`，按北京时间包含起止当天 |

页面默认查询工作日志（`objectType=LOG`），重置筛选后同样回到工作日志。每次请求都明确限定 `LOG` 或 `TASK`，不提供不限定类型的全部查询，不接受 `PERSONAL_TASK`。其他空筛选参数不发送。

仅使用现有单类型查询，不在前端拼接多次请求或过滤单页后伪造总数。后端如果忽略类型筛选，前端明确报错，不展示混入的其他业务记录。

分页 `data` 为 `{items,page,size,total}`。`total` 必须是应用全部查询条件后的记录数，排序须稳定，建议时间倒序、记录编号倒序。筛选条件由服务端执行。

## 列表和详情

`GET /api/audits/{id}` 返回单条详情，列表 `items` 和详情共用下面的基础字段：

| 字段 | 约定 |
| --- | --- |
| `id` | 审计记录编号 |
| `actor` | 可识别的操作人文字，建议姓名和账号；人员停用后仍能追溯 |
| `action` | 动作文字，例如“新增日志”“修改日志”“删除任务” |
| `target` | 操作对象的可读说明 |
| `time` | 带时区的 ISO 时间，前端按北京时间显示 |
| `result` | `SUCCESS` / `FAILED`，兼容原有“成功” / “失败” |
| `objectType`、`objectId` | 业务类型和业务编号；类型必须准确返回，历史记录由服务端归类，不能把未知类型混入日志或任务 |
| `source` | `USER` 用户操作、`SYSTEM` 系统自动处理；未知值按原值显示，缺失显示未记录 |
| `summary` | 简要说明，不含密码、令牌、完整证件号或业务正文 |

详情额外返回 `changes: [{field,before,after}]`。`field` 为字符串，`before`、`after` 为字符串或 `null`。历史数据缺少 `changes` 或返回 `null` 时，页面显示没有字段变化详情；错误的数组结构明确报错。

前端已识别 `status`、`executionStatus`、`reviewStatus`、`name`、`content`、`details` 等常用字段；未知字段和枚举按原值展示。正文变化仅需返回“已修改”等标记，不复制正文。

任务删除后，对应记录及详情仍应可查询；详情查询不应依赖任务当前还存在。失败操作是否留痕及失败原因由服务端确定，失败记录不能当作成功删除。

下面为虚构的任务删除详情示例，只用于核对字段，不表示真实操作已发生；`changes` 可以为空，不要求为了删除操作复制完整任务内容：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": "1001",
    "actor": "示例组长（sample_leader）",
    "action": "删除任务",
    "target": "派发任务 #42",
    "time": "2026-11-02T10:00:00+08:00",
    "result": "SUCCESS",
    "objectType": "TASK",
    "objectId": "42",
    "source": "USER",
    "summary": "删除示例派发任务",
    "changes": []
  }
}
```

## 其他需要后端核对的前端约束

管理员新开户已将 `POST /api/users` 的 `idNumber` 设为必填。后端同学需核对最终交付版本同样校验：去除首尾空格、末位小写 `x` 转 `X`、18位结构、有效且不晚于当天的出生日期及校验位。前端校验不能代替服务端校验，号码格式有效也不等于实名核验。

性别仍选填，不默认替员工选“男”。既有账号不增加身份证补录接口或“待补全”流程，不编造真实员工证件；认证摘要和审计不返回或保存完整号码。这部分是管理员开户接口协作要求，不要求移动端新增员工资料维护入口。

## 联调验收

1. 不同角色在真实手机端新增日志、修改草稿、派发任务、更新进度后，管理员能按操作者、类型、日期和动作查到对应记录。
2. 手机端完成任务删除后，可查到成功删除记录，业务编号准确，任务删除后详情仍可打开；日志没有删除入口。
3. 默认进入及重置后只查询工作日志；类型选项只包含工作日志、派发任务，不能出现自建任务或其他管理记录。超过一页时筛选、总数和翻页准确；切换类型回到第一页并保留其他条件。
4. 403、404、500、网络失败显示错误并可重试，不自动回退演示数据；没有匹配数据时才显示空态。
5. 生产构建隐藏演示和自检入口，真实接口失败不会生成本地记录。前端夹具测试只验证展示与请求，不代替手机端、服务端联调。
6. 按双方确认的权限及状态矩阵验证任务删除；无权限或状态不允许时不能成功删除，也不能产生成功删除审计。重复删除不得产生多次实际删除或多条成功删除记录。
7. 后端独立验证新开户身份证缺失、非法日期、错误校验位及小写 `x` 归一化，不依赖 Web 表单阻拦；性别为空仍可按约定开户。
