## 前端动作与移动端写请求

路径均带 `/api` 前缀。第一列是管理员端动作筛选发送的 `action` 值，后端审计动作文字应与之对应。所有角色的实际操作都按业务权限留痕。

| 记录类型与动作 | 移动端入口和条件 | 请求 |
| --- | --- | --- |
| `LOG` 新增日志 | 首次写当天日志，保存草稿或正式提交前先创建 | `POST /logs` |
| `LOG` 修改日志 | 编辑本人已有日志并保存。App 也有近三天已提交日志的编辑入口，当前后端仅允许草稿 | `PUT /logs/{id}` |
| `LOG` 提交日志 | 点击正式提交，先保存正文，再提交草稿 | `POST /logs/{id}/submit` |
| `LOG` 日志点评 | 直属上级发送点评 | `POST /logs/{id}/comments`，无父点评 |
| `LOG` 回复点评 | 日志作者选择上级的点评并回复 | `POST /logs/{id}/comments`，带 `parentId` |
| `TASK` 提交派发申请 | 新建派发，从人员列表选接收人后提交 | `POST /tasks/dispatch-requests` |
| `TASK` 编辑待审派发申请 | 在本人发布记录中编辑待审申请 | `PUT /tasks/dispatch-requests/{requestId}` |
| `TASK` 撤回派发申请 | 在本人发布记录中撤回待审申请 | `DELETE /tasks/dispatch-requests/{requestId}`，返回 `WITHDRAWN` |
| `TASK` 提交修改申请 | 编辑本人已发布且无待审变更的任务 | `POST /tasks/{taskId}/change-requests`，`action=UPDATE` |
| `TASK` 提交删除申请 | 对本人已发布且无待审变更的任务申请删除 | `POST /tasks/{taskId}/change-requests`，`action=DELETE`，返回 `PENDING` |
| `TASK` 更新进度 | 接收人将任务标记为进行中或已完成 | `POST /tasks/assignments/{assignmentId}/progress-updates` |
| `TASK` 申请完成检查 | 接收人完成任务后，尚未申请或被退回时可申请 | `POST /tasks/assignments/{assignmentId}/review-invitations` |
| `TASK` 通过检查 | 派发人处理待检查任务 | `POST /tasks/assignments/{assignmentId}/review`，`result=APPROVED` |
| `TASK` 退回检查 | 派发人处理待检查任务，填写退回原因 | 同一检查接口，`result=RETURNED` |

一次「正式提交」可能产生保存和提交两条成功记录。任务完成检查与派发或变更申请审批属于不同流程。撤回待审申请只改变申请状态。实际删除在服务端审批生效后单独记为「删除任务」，管理员可在「全部动作」中查询。日志禁止删除。 [日志页面](https://github.com/wang0166/Software-Testing/blob/8c23d2c/mobile/lib/screens/logs_page.dart) · [日志详情](https://github.com/wang0166/Software-Testing/blob/8c23d2c/mobile/lib/screens/log_detail_page.dart) · [任务页面](https://github.com/wang0166/Software-Testing/blob/8c23d2c/mobile/lib/screens/tasks_page.dart) · [真实请求](https://github.com/wang0166/Software-Testing/blob/8c23d2c/mobile/lib/data/api_repository.dart)

## 功能边界

- 管理员在 Web `/audits` 查询手机端各角色对日志、任务的新增和修改记录，以及任务删除记录。日志不开放删除。
- 页面只包含工作日志、派发任务，不提供自建任务、员工账号、组织、公司事项、密码申请或本地维护等其他记录入口。
- Web 只提供查询、筛选、分页和详情，不执行日志或任务的新增、修改、删除，也不提供数据恢复。
- 记录生成、完整性、权限和任务删除规则由后端负责；手机端负责业务操作入口。前端展示接口实际返回的记录，不根据按钮点击自行生成真实审计。
- 已发布任务的删除申请与实际删除分别展示。联调以服务端返回的审批结果和审计为准。

## 查询接口

沿用统一 `/api` 前缀、Bearer 认证及 `{code,message,data}` 响应。

`GET /api/audits`

| 查询参数 | 含义 |
| --- | --- |
| `page`、`size` | 从 1 开始的页码、每页条数；页面每页 10 条 |
| `actor` | 操作者姓名或账号，可查询所有角色，不只管理员 |
| `action` | 上表的完整动作文字，例如 `编辑待审派发申请`。应按动作区分记录，省略时返回该类型的所有动作 |
| `objectType` | 单个业务类型；只允许 `LOG` 工作日志、`TASK` 派发任务 |
| `from`、`to` | `YYYY-MM-DD`，按北京时间包含起止当天 |

页面默认查询工作日志（`objectType=LOG`），重置筛选后同样回到工作日志。每次请求都明确限定 `LOG` 或 `TASK`，不提供不限定类型的全部查询，不接受 `PERSONAL_TASK`。其他空筛选参数不发送。

仅使用现有单类型查询，不在前端拼接多次请求或过滤单页后伪造总数。后端如果忽略类型筛选，前端明确报错，不展示混入的其他业务记录。

分页 `data` 为 `{items,page,size,total}`。`total` 必须是应用全部查询条件后的记录数，排序须稳定，建议时间倒序、记录编号倒序。筛选条件由服务端执行。

## 列表和详情

`GET /api/audits/{id}` 返回单条详情，列表 `items` 和详情共用下面的基础字段：

| 字段 | 约定 |
| --- | --- |
| `id` | 审计记录编号 |
| `actor` | 可识别的操作人文字，建议姓名和账号；人员停用后仍能追溯 |
| `action` | 动作文字，例如“新增日志”“修改日志”“删除任务” |
| `target` | 操作对象的可读说明 |
| `time` | 带时区的 ISO 时间，前端按北京时间显示 |
| `result` | `SUCCESS` / `FAILED`，兼容原有“成功” / “失败” |
| `objectType`、`objectId` | 业务类型和业务编号；类型必须准确返回，历史记录由服务端归类，不能把未知类型混入日志或任务 |
| `source` | `USER` 用户操作、`SYSTEM` 系统自动处理；未知值按原值显示，缺失显示未记录 |
| `summary` | 简要说明，不含密码、令牌、完整证件号或业务正文 |

详情额外返回 `changes: [{field,before,after}]`。`field` 为字符串，`before`、`after` 为字符串或 `null`。历史数据缺少 `changes` 或返回 `null` 时，页面显示没有字段变化详情；错误的数组结构明确报错。

前端已识别 `status`、`executionStatus`、`reviewStatus`、`name`、`content`、`details` 等常用字段；未知字段和枚举按原值展示。正文变化仅需返回“已修改”等标记，不复制正文。

任务删除后，对应记录及详情仍应可查询；详情查询不应依赖任务当前还存在。失败操作是否留痕及失败原因由服务端确定，失败记录不能当作成功删除。

下面为虚构的任务删除详情示例，只用于核对字段，不表示真实操作已发生；`changes` 可以为空，不要求为了删除操作复制完整任务内容：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": "1001",
    "actor": "示例组长（sample_leader）",
    "action": "删除任务",
    "target": "派发任务 #42",
    "time": "2026-11-02T10:00:00+08:00",
    "result": "SUCCESS",
    "objectType": "TASK",
    "objectId": "42",
    "source": "USER",
    "summary": "删除示例派发任务",
    "changes": []
  }
}
```

## 其他需要后端核对的前端约束

管理员新开户已将 `POST /api/users` 的 `idNumber` 设为必填。后端同学需核对最终交付版本同样校验：去除首尾空格、末位小写 `x` 转 `X`、18位结构、有效且不晚于当天的出生日期及校验位。前端校验不能代替服务端校验，号码格式有效也不等于实名核验。

性别仍选填，不默认替员工选“男”。既有账号不增加身份证补录接口或“待补全”流程，不编造真实员工证件；认证摘要和审计不返回或保存完整号码。这部分是管理员开户接口协作要求，不要求移动端新增员工资料维护入口。

## 联调验收

1. 使用测试账号在真实手机端新增、修改、提交日志，分别点评和回复。管理员按操作者、日期和动作逐项查到对应记录。按双方确定的规则验证已提交日志编辑及越权拒绝。
2. 分别验证派发申请的提交、编辑和撤回，已发布任务的修改和删除申请，以及进度、申请完成检查、通过与退回。删除审批前任务保持有效，删除生效后仍能按业务编号查询成功删除的记录和详情。
3. 默认进入及重置后只查询工作日志；类型选项只包含工作日志、派发任务，不能出现自建任务或其他管理记录。超过一页时筛选、总数和翻页准确；切换类型回到第一页并保留其他条件。
4. 403、404、500、网络失败显示错误并可重试，不自动回退演示数据；没有匹配数据时才显示空态。
5. 生产构建隐藏演示和自检入口，真实接口失败不会生成本地记录。前端夹具测试只验证展示与请求，不代替手机端、服务端联调。
6. 按双方确认的权限及状态矩阵验证任务删除；无权限或状态不允许时不能成功删除，也不能产生成功删除审计。重复删除不得产生多次实际删除或多条成功删除记录。
7. 后端独立验证新开户身份证缺失、非法日期、错误校验位及小写 `x` 归一化，不依赖 Web 表单阻拦；性别为空仍可按约定开户。
