## 2. 设计目标与原则

### 2.1 设计目标

1. 形成「登录 → 新建日志 → 草稿 → 提交 → 按角色查看 → 点评 → 统计」的完整可运行闭环。
2. 将权限（数据可见范围）统一收敛到服务端，前端只做展示与路由控制，杜绝越权访问。
3. 保证日志「每人每天一条」「日期取当天」「提交后不可修改」「截止自动处理」等核心规则在数据库和业务层双重约束。
4. 保持架构简单、可测试、可容器化部署，满足实训中对安全、性能、可靠性、隐私等非功能要求。

### 2.2 设计原则

- **服务端强制鉴权与过滤**：所有写接口校验身份，所有读接口按角色/归属拼接过滤条件。
- **数据库兜底**：用唯一约束、非空约束、检查约束保证数据一致性，不依赖前端。
- **明确边界**：前端只负责交互与展示，权限规则、状态流转、统计口径由后端定义。
- **可观测**：关键管理操作写审计日志，异常与登录失败可追踪。
- **可演进**：角色固定、功能权限可配置；数据范围与功能开关分离，便于后续扩展。

## 3. 总体架构

系统采用前后端分离的三层架构，全部服务容器化。

```text
┌──────────────────────────┐        ┌──────────────────────────┐
│     Flutter Android 端    │        │      React Web 管理端      │
│ 员工/团队长/部门老总/创始人 │        │        系统管理员           │
└────────────┬─────────────┘        └────────────┬─────────────┘
             │            HTTPS / REST / JSON     │
             └──────────────────┬─────────────────┘
                                ▼
                 ┌──────────────────────────────┐
                 │       Java Spring Boot        │
                 │  认证 / 用户 / 组织 / 角色权限 / │
                 │  日志 / 点评 / 任务 / 展示内容 /   │
                 │  统计 / 配置 / 审计 / 日历地图    │
                 │  （REST API + 服务端数据过滤）  │
                 └──────────────┬───────────────┘
                                │ JDBC / MyBatis
                                ▼
                 ┌──────────────────────────────┐
                 │          PostgreSQL           │
                 │  业务数据 + 配置 + 审计 + 令牌    │
                 └──────────────────────────────┘
```

组件职责：

| 组件 | 职责 |
|---|---|
| Flutter Android 端 | 员工、团队长、部门老总、创始人的日志填报、查看、点评、统计、任务派发与接收、自建任务、公司展示内容、日历与数据地图 |
| React Web 管理端 | 系统管理员的用户/组织/角色/配置管理、日志与统计只读查看、公司十大重要事项维护 |
| Spring Boot 后端 | 认证鉴权、业务规则、数据权限过滤、任务状态机、定时任务、审计，统一 REST API |
| PostgreSQL | 持久化全部业务数据、配置、审计记录与刷新令牌 |

客户端不直接访问数据库，所有数据请求经后端 RESTful API，由后端统一强制校验。

| 层面 | 选型 | 选型理由 |
|---|---|---|
| 移动客户端 | Flutter（Dart） | 单套代码覆盖 Android，适合表单/列表类应用，开发效率高 |
| Web 管理端 | React + JavaScript | 组件化、生态成熟，适合管理后台 |
| 后端 | Java + Spring Boot | 成熟稳定，安全与事务支持好，团队熟悉 |
| 数据持久层 | MyBatis | SQL 可控，便于实现服务端数据权限拼接与复杂统计 |
| 数据库 | PostgreSQL | 强约束（唯一/检查/外键），事务可靠，适合关系型业务 |
| 构建工具 | Maven | 与 Spring Boot 生态契合 |
| 认证 | JWT 访问令牌 + 刷新令牌 | 移动端无状态调用友好，支持登出与刷新 |

## 5. 后端设计

### 5.1 分层架构与包结构

```text
│   ├── ApiResponse.java    # 统一响应
│   ├── ErrorCode.java      # 错误码枚举
│   ├── BusinessException.java
│   ├── PageResult.java
│   └── CurrentUser.java    # 当前登录上下文
```

### 5.2 统一响应与错误码

所有接口返回统一结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": { }
}
```

分页数据统一为：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "total": 120,
    "page": 1,
    "size": 20,
    "items": []
  }
}
```

错误码分段（示例）：

| 分段 | 含义 |
|---|---|
| 0 | 成功 |
| 40001–40099 | 参数错误（内容为空、日期非法等） |
| 40100–40199 | 认证失败（未登录、令牌过期、登录被锁定） |
| 40300–40399 | 无权限（越权访问、非本人操作） |
| 40400–40499 | 资源不存在 |
| 40900–40999 | 业务冲突（当日已提交、重复创建等） |
| 50000–50099 | 服务内部错误 |

### 5.3 认证与授权

#### 5.3.1 令牌模型

- **访问令牌（access token）**：JWT，短时效（默认 120 分钟），签名算法 HS256，载荷包含 `userId`、`username`、`role`、`departmentId`、`teamId`、`exp`。用于每次 API 鉴权。
- **刷新令牌（refresh token）**：随机不透明字符串，仅在服务端保存哈希，默认 7 天有效，用于换取新访问令牌；登出即吊销。

#### 5.3.2 密码与登录保护

- 密码使用 BCrypt（强度 10）存储，仅保存 `password_hash`。
- 连续登录失败达到阈值（默认 5 次）后，账号进入锁定状态并记录 `locked_until`，锁定默认 15 分钟；成功后清零失败计数。
- 锁定状态由服务端校验，前端只展示提示。

#### 5.3.3 授权模型

授权分两层：

1. **功能权限**：每个受保护接口标注所需权限码，服务端通过 `role_permissions` 校验用户角色是否具备该权限。
2. **数据范围**：通过角色码动态拼接查询条件（见 6 与 5.4）。

权限码（功能开关）：

| 权限码 | 说明 |
|---|---|
| `user:manage` | 用户管理 |
| `org:manage` | 组织管理 |
| `role:manage` | 角色权限管理 |
| `config:manage` | 系统配置管理 |
| `audit:read` | 审计查询 |
| `log:write` | 日志填写 |
| `log:read` | 日志查看 |
| `comment:write` | 点评与回复 |
| `stats:read` | 统计查看 |
| `task:dispatch` | 查询直接下级、派发任务、编辑任务内容、查看派发列表、检查接收人 |
| `task:execute` | 查看本人接收任务、更新本人进度、发起检查邀约、读取数据地图与日历任务 |
| `task:self` | 新增、查看、编辑本人自建任务 |
| `content:read` | 读取公司十大重要事项与公司十大重要任务 |
| `company-matter:manage` | 维护公司十大重要事项 |
| `company-task:manage` | 维护公司十大重要任务 |

任务接口在功能权限码之外还必须执行对象级鉴权：派发人只能访问 `sender_id = 当前用户` 的任务，接收人只能访问 `assignee_id = 当前用户` 的接收记录，展示内容只有对应发布者可以维护。管理员不具备任务相关权限码，其日志只读权限不扩展到任务数据。

### 5.4 数据权限过滤实现

日志查询在 Service 层根据当前用户角色拼接过滤条件，Mapper 通过动态 SQL 应用。规则：

```text
员工       -> author_id = :me
团队长     -> author.team_id = :myTeamId
部门老总   -> author.department_id = :myDepartmentId
创始人     -> 不过滤（全公司）
系统管理员 -> 不过滤（全公司，只读）
```

伪 SQL：

```sql
SELECT * FROM work_logs w
JOIN users u ON u.id = w.author_id
WHERE 1 = 1
  -- 员工
  AND u.id = #{me}
  -- 团队长
  AND u.team_id = #{myTeamId}
  -- 部门老总
  AND u.department_id = #{myDepartmentId}
  -- 创始人 / 管理员：不拼接过滤条件
ORDER BY w.log_date DESC, w.id DESC;
```

任务数据不沿用日志可见范围，而是按对象归属过滤：

```text
派发任务列表   -> tasks.sender_id = :me
任务详情/编辑  -> tasks.sender_id = :me
本人接收列表   -> task_assignments.assignee_id = :me
进度/邀约      -> task_assignments.assignee_id = :me
派发人检查     -> task_assignments.task_id 属于 tasks.sender_id = :me
自建任务       -> personal_tasks.owner_id = :me
数据地图       -> 本人接收记录 UNION 本人自建任务
日历任务       -> 本人接收记录且日期范围相交
```

管理员不参与任务查询；任何请求中的 `assigneeId`、`senderId`、`ownerId` 参数都不得扩大上述服务端条件。

### 5.5 事务与并发控制

- 新建/编辑/提交日志在事务内执行；提交时先按 `author_id + log_date` 查询并加锁（`SELECT ... FOR UPDATE`），避免重复提交或重复创建。
- 数据库层 `UNIQUE(author_id, log_date)` 作为最终兜底。
- 提交状态流转使用条件更新（`WHERE status = 'DRAFT'`），保证幂等。

任务模块的并发控制：

- 派发任务在一个事务内完成：先一次性校验全部接收人，再插入 `tasks` 与 `task_assignments`，任一人非法则整体回滚，不产生部分接收记录。
- `UNIQUE(task_id, assignee_id)` 防止同一任务对同一接收人重复派发。
- 更新进度使用条件更新，例如 `WHERE id=? AND assignee_id=? AND execution_status=? AND review_status IN ('NONE','RETURNED')`；相同状态重复请求按幂等成功处理。
- 发起邀约使用 `WHERE id=? AND assignee_id=? AND execution_status='COMPLETED' AND review_status IN ('NONE','RETURNED')`，只有一个并发请求能把状态改为 `PENDING`。
- 派发人检查使用 `WHERE id=? AND review_status='PENDING'`，并先确认该接收记录所属任务的 `sender_id` 为当前用户；并发重复检查只有一个成功。
- `task_reviews` 为 append-only 历史，只追加不覆盖；退回后再次完成并邀约时新增 `INVITED` 记录。

### 5.6 定时任务（截止自动处理）

使用 Spring `@Scheduled` 每分钟执行一次，读取 `system_configs['log_deadline']`，按 `Asia/Shanghai` 时区判断是否到达截止时间，处理逻辑幂等：

```text
每 1 分钟:
  deadline = config('log_deadline')   -- 默认 22:00
  if now(tz) >= deadline:
    将 log_date = 今天 且 status = 'DRAFT' 的日志
    UPDATE 为 status = 'SUBMITTED', submitted_at = 截止时刻
```

未提交不落库，由「当日无记录且已过截止时间」推导得出。截止后新建/编辑/提交接口均返回「已过截止时间，不可操作」。

### 5.7 审计

管理员的关键写操作（创建/停用用户、维护组织、修改角色权限、修改系统配置）通过 AOP 切面写入 `operation_audits`，记录操作人、操作类型、对象、结果、IP、时间。日志正文的修改/删除不开放给管理员，因此不产生对应审计记录。

### 5.8 配置管理

系统参数存于 `system_configs`，常用项：

| key | 默认值 | 说明 |
|---|---|---|
| `log_deadline` | `22:00` | 日志提交截止时间 |
| `login_max_failures` | `5` | 登录失败锁定阈值 |
| `login_lock_minutes` | `15` | 锁定分钟数 |
| `access_token_ttl_minutes` | `120` | 访问令牌有效期 |
| `refresh_token_ttl_days` | `7` | 刷新令牌有效期 |

## 6. 数据库设计

### 6.1 设计约定

- 主键统一 `BIGSERIAL`。
- 时间统一 `TIMESTAMPTZ`，业务日期使用 `DATE`。
- 角色、状态、权限等使用 `VARCHAR` 枚举并加 `CHECK` 约束，避免魔法数字。
- 组织/用户间存在循环引用（创始人/部门老总/团队长指向 users，users 又指向部门/团队），在第二次迁移中用 `ALTER TABLE` 追加外键。

### 6.2 ER 关系图

```text
┌───────────┐ 1     1 ┌────────────┐ 1    * ┌────────────┐ 1    * ┌────────┐
│ companies │─────────│ departments│───────│   teams    │───────│  users │
└─────┬─────┘         └─────┬──────┘        └─────┬──────┘        └──┬───┬──┘
      │ founder_id          │ manager_id         │ leader_id        │   │
      └─────────────────────┴────────────────────┴──────────────────┘   │
                                                                       │
                                     ┌─────────────────────────────────┘
                                     ▼ 1
                            ┌──────────────┐ 1   * ┌──────────────┐
                            │  work_logs   │───────│ log_comments │
                            └──────────────┘       └──────┬───────┘
                                                            │ parent_id（自关联）
                                                            └───────┘

任务与展示内容关系：

users 1 ────── * tasks（sender_id）
users 1 ────── * task_assignments（assignee_id）
tasks 1 ────── * task_assignments（task_id，任务 + 接收人唯一）
task_assignments 1 ── * task_reviews（assignment_id，append-only）
users 1 ────── * personal_tasks（owner_id，仅本人可见）
users 1 ────── * company_matters（updated_by，管理员维护）
users 1 ────── * company_important_tasks（updated_by，创始人维护）
```

`personal_tasks` 不与 `tasks`/`task_assignments` 关联；`company_matters` 与 `company_important_tasks` 也不与任务表关联，避免公司展示内容被当作常规任务参与派发、统计、日历或数据地图。

### 6.3 表结构（DDL）

#### 6.3.1 公司、部门、团队

```sql
CREATE TABLE companies (
  id         BIGSERIAL PRIMARY KEY,
  name       VARCHAR(100) NOT NULL,
  founder_id BIGINT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE departments (
  id         BIGSERIAL PRIMARY KEY,
  company_id BIGINT NOT NULL REFERENCES companies(id) ON DELETE RESTRICT,
  name       VARCHAR(100) NOT NULL,
  manager_id BIGINT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT ux_departments_name UNIQUE (company_id, name)
);

CREATE TABLE teams (
  id            BIGSERIAL PRIMARY KEY,
  department_id BIGINT NOT NULL REFERENCES departments(id) ON DELETE RESTRICT,
  name          VARCHAR(100) NOT NULL,
  leader_id     BIGINT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT ux_teams_name UNIQUE (department_id, name)
);
```

#### 6.3.2 用户、角色、权限

```sql
CREATE TABLE users (
  id             BIGSERIAL PRIMARY KEY,
  username       VARCHAR(64) NOT NULL UNIQUE,
  password_hash  VARCHAR(100) NOT NULL,
  real_name      VARCHAR(64) NOT NULL,
  role_code      VARCHAR(32) NOT NULL,
  department_id  BIGINT REFERENCES departments(id) ON DELETE RESTRICT,
  team_id        BIGINT REFERENCES teams(id) ON DELETE RESTRICT,
  status         VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
  failed_attempts INT NOT NULL DEFAULT 0,
  locked_until   TIMESTAMPTZ,
```

### 6.6 数据一致性要点

- `UNIQUE(author_id, log_date)` 保证每人每天一条。
- `CHECK (btrim(content) <> '')` 保证日志与点评内容非空。
- `CHECK` 约束限制角色、状态取值合法。
- `UNIQUE(task_id, assignee_id)` 保证同一任务对同一接收人只有一条接收记录；`CHECK (deadline >= start_date)` 保证截止日期不早于开始日期。
- 任务状态、检查状态、紧急程度和检查动作均由 `CHECK` 约束限制取值；`task_reviews` 只追加，不更新或删除历史。
- 公司展示内容使用独立表，不设置指向 `tasks` 的外键，从数据层防止其混入任务派发、统计、日历或数据地图。
- 组织删除使用 `RESTRICT`，存在成员/子级时禁止删除，避免悬挂引用。

### 7.7 任务派发接口

任务对象字段：`id`、`senderId`、`name`、`details`、`startDate`、`deadline`、`urgency`、`createdAt`、`updatedAt`。任务内容由派发人维护，向一个或多个直接下级派发；每名接收人对应一条独立接收记录，进度与检查状态互不影响。

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/tasks/recipients` | `task:dispatch` | 当前用户可派发的直接下级（仅启用账号） |
| POST | `/api/tasks` | `task:dispatch` | 派发任务，一次创建共享内容与多条接收记录 |
| GET | `/api/tasks/dispatched` | `task:dispatch` | 本人派发的任务列表，含接收人汇总 |
| GET | `/api/tasks/{taskId}` | `task:dispatch` | 派发任务详情，含全部接收记录 |
| PUT | `/api/tasks/{taskId}` | `task:dispatch` | 编辑共享任务内容 |

直接下级范围：

```text
FOUNDER      -> 全部启用状态的部门老总
DEPT_MANAGER -> 本部门启用状态的团队长
TEAM_LEADER  -> 本团队启用状态的员工
EMPLOYEE     -> 无可派发对象
ADMIN        -> 不可派发
```

**POST /api/tasks** 请求：

```json
{
  "name": "完成10月经营分析",
  "details": "汇总各团队数据并输出报告",
  "startDate": "2026-10-20",
  "deadline": "2026-10-25",
  "urgency": "URGENT",
  "assigneeIds": [12, 13]
}
```

校验规则：

- `name`、`details` 去空格后不得为空；`name` 最长 200 字符。
- `startDate`、`deadline` 为 `YYYY-MM-DD`，且 `deadline >= startDate`。
- `urgency` 只能为 `URGENT` 或 `NOT_URGENT`。
- `assigneeIds` 至少一人、不得重复，且全部为当前用户的直接下级启用账号。
- 任一接收人不合法时整单拒绝；服务端在一个事务内创建一条 `tasks` 和多条 `task_assignments`，接收记录初始为 `NOT_STARTED/NONE`。

派发列表与详情字段、汇总口径（`assigneeCount`、`completedCount`、`pendingReviewCount`）见 [后端接口文档.md](file:///C:/Users/ASUS/software-testing/Software-Testing/documents/后端接口文档.md#L207-L258)。编辑接口只修改共享内容，不改变任何接收人的执行状态或检查状态，当前版本不提供增删接收人。

| GET | `/api/tasks/received` | `task:execute` | 本人接收任务列表，可按执行/检查状态筛选 |
| GET | `/api/tasks/assignments/{assignmentId}` | `task:execute` | 本人接收任务详情与检查历史 |
| PATCH | `/api/tasks/assignments/{assignmentId}/progress` | `task:execute` | 更新本人执行进度 |
| POST | `/api/tasks/assignments/{assignmentId}/review-invitations` | `task:execute` | 完成邀约派发人检查 |
| POST | `/api/tasks/assignments/{assignmentId}/review` | `task:dispatch` | 派发人通过或退回 |

状态枚举：

| 枚举 | 取值 |
|---|---|
| 执行状态 `executionStatus` | `NOT_STARTED`、`IN_PROGRESS`、`COMPLETED` |
| 检查状态 `reviewStatus` | `NONE`、`PENDING`、`APPROVED`、`RETURNED` |
| 检查动作 `action` | `INVITED`、`APPROVED`、`RETURNED` |

允许转换与冲突语义：

- 进度仅允许 `NOT_STARTED → IN_PROGRESS`、`IN_PROGRESS → COMPLETED`；相同状态重复提交按幂等成功处理，其他转换返回 409 `40910`。
- `reviewStatus` 为 `PENDING` 或 `APPROVED` 时禁止修改进度。
- 邀约要求 `executionStatus=COMPLETED` 且 `reviewStatus ∈ {NONE, RETURNED}`；`PENDING` 返回 409 `40911`，`APPROVED` 返回 409 `40912`。
- 检查要求 `reviewStatus=PENDING`：`APPROVED` 保持执行状态为 `COMPLETED`；`RETURNED` 将检查状态置为 `RETURNED`、执行状态回到 `IN_PROGRESS`，接收人可修改后再次邀约。
- 每次邀约或检查向 `task_reviews` 追加一条记录，历史只追加不修改。

## 8. 核心业务流程设计

### 8.1 登录与令牌

```text
App                      AuthController          AuthService                 DB
 │--login(username,pwd)-->      │--authenticate-->│--findUser(username)------>│
 │                             │                 │<--user / password_hash-----│
 │                             │                 │--BCrypt.matches()-->       │
 │                             │                 │--gen access + refresh-->   │
 │<--accessToken+refreshToken--│<--tokens+user---│<--store refresh hash-----│
```

失败处理：校验失败时 `failed_attempts + 1`，达到阈值写入 `LOCKED` 与 `locked_until`；成功则清零。停用账号直接拒绝登录。

### 8.2 日志生命周期

```text
新建（内容非空，日期=今天）
      │
      ▼
   草稿 ──编辑（仅作者，截止前）──▶ 草稿
      │
      ├── 正式提交 ──▶ 已提交（不可修改）
      │
      └── 到截止时间（有草稿）──▶ 自动作为当日日志（已提交）

截止时间（无草稿）──▶ 未提交（不可补交，由推导得出）
```

关键校验：

- 新建：当天是否已存在记录（作者 + 日期唯一）；日期强制取服务端当天；内容非空。
- 编辑：仅作者、仅 `DRAFT`、截止前。
- 提交：仅作者、仅 `DRAFT`、截止前，条件更新为 `SUBMITTED`。

### 8.3 截止自动处理

```text
22:00（可配置）
      │
      ▼
┌─────────────────────────────┐
│ 扫描今日 DRAFT 日志          │
│ UPDATE -> SUBMITTED          │
└─────────────────────────────┘
      │
      ├── 有草稿 -> 已提交
      └── 无草稿 -> 未提交（推导）
```

### 8.4 点评对话

```text
员工提交日志
      │
      ▼
团队长（直接上级）发起点评  ── 校验：评论人 == 日志作者直接上级
      │
      ▼
员工回复（parent_id 指向上级点评）
      │
      └─ 对话仅「日志作者 + 日志作者直接上级」可见/可参与
```

可见性校验：查询或新增评论前，服务端确认当前用户属于 `{日志作者, 日志作者直接上级}`，否则返回 403。更上级（部门老总看团队长点评员工、创始人看部门老总点评团队长）不可见、不可参与。创始人无直接上级，其日志无人可点评。

直接上级解析：

```text
员工       -> 所在团队 teams.leader_id
团队长     -> 所在部门 departments.manager_id
部门老总   -> 公司 companies.founder_id
创始人     -> 无
系统管理员 -> 无
```

### 8.5 任务派发与逐接收人检查

```text
选择直接下级（worker 校验角色与组织）
      │
      ▼
派发任务（事务：1 条 tasks + N 条 task_assignments）
      │
      ▼
接收人 A                    接收人 B
  │ 更新进度                  │ 更新进度
  │ NOT_STARTED→IN_PROGRESS   │ 独立状态
  │ IN_PROGRESS→COMPLETED     │
  │ 完成邀约（PENDING）        │
  ▼                           ▼
派发人检查 A                 派发人检查 B
  ├─ 通过 → APPROVED          ├─ 通过 → APPROVED
  └─ 退回 → RETURNED          └─ 退回 → RETURNED
             且执行状态回到 IN_PROGRESS
```

关键校验：

- 派发：`assigneeIds` 全部为当前用户的直接下级且启用，重复或为空返回 400 `40003`，非直接下级返回 403 `40310`；任一失败整单回滚。
- 进度：仅接收人本人，条件更新 `WHERE id = ? AND assignee_id = ? AND review_status IN ('NONE','RETURNED')`，并按当前执行状态限制允许的目标状态。
- 邀约：仅接收人本人，条件更新 `WHERE id = ? AND assignee_id = ? AND execution_status = 'COMPLETED' AND review_status IN ('NONE','RETURNED')`，成功后追加 `task_reviews(INVITED)`。
- 检查：仅任务派发人，条件更新 `WHERE id = ? AND review_status = 'PENDING'` 并校验 `task.sender_id = 当前用户`；通过保持 `COMPLETED`，退回改为 `IN_PROGRESS`，同一事务追加检查历史。
- 并发：条件更新影响行数为 0 时，按当前状态返回 409 `40910`/`40911`/`40912`，不覆盖他人已提交的结果。
- 退回重提：`RETURNED` 允许接收人修改进度并再次邀约，检查历史保留全部轮次。

对象级鉴权说明：任务接口同时校验功能权限码与对象归属。派发人只能访问 `sender_id = 当前用户` 的任务；接收人只能访问 `assignee_id = 当前用户` 的接收记录；系统管理员无任务功能权限，不得查看或操作他人任务。

### 8.6 统计计算

```text
个人：应提交=1，按本人当日日志状态计算
团队：应提交=本团队全部需写日志用户，已提交=当日 SUBMITTED 人数
部门：应提交=本部门全部需写日志用户
公司：应提交=全公司除管理员外用户
```

规模较小时实时 SQL 聚合即可，无需预聚合表。

- 公司十大重要事项维护入口仅管理员可见，调用 `company-matter:manage`；公司十大重要任务由创始人在 Android 端维护，Web 端不提供入口。
- 管理员不提供任务查看、派发、接收或检查页面；后端同样拒绝任务接口。
- 页面操作调用对应管理接口，后端 `user:manage` 等权限兜底。

## 11. 关键设计决策（ADR）

| 编号 | 决策 | 备选 | 结论与理由 |
|---|---|---|---|
| ADR-01 | JWT 访问令牌 + 刷新令牌 | 服务端 Session | JWT 无状态，适配移动端；刷新令牌落库支持吊销与登出 |
| ADR-02 | 密码 BCrypt 存储 | MD5/SHA | BCrypt 加盐、抗暴力，安全性达标 |
| ADR-03 | MyBatis 而非 JPA | Spring Data JPA | SQL 显式，便于拼接数据权限与统计口径 |
| ADR-04 | 未提交由规则推导，不落库 | 新增未提交记录表 | 减少状态同步成本，口径统一由「当日无记录且过截止」判断 |
| ADR-05 | 每分钟定时扫描处理截止 | 单次 cron 定时 | 支持管理员动态改截止时间，幂等更新保证安全 |
| ADR-06 | 功能权限与数据范围分离 | 单一 RBAC | 角色码定数据范围，权限码定功能开关，职责清晰 |
| ADR-07 | PostgreSQL 而非 MySQL | MySQL | 强约束与事务模型更适合关系型、多组织数据 |
| ADR-08 | 不引入消息队列 | 引入 MQ | 并发极小，同步处理足够，降低复杂度 |
| ADR-09 | 共享任务 `tasks` 与接收记录 `task_assignments` 分离 | 每个接收人复制一条完整任务 | 任务内容只维护一份，进度与检查状态按接收人独立；`(task_id, assignee_id)` 唯一约束防止重复派发 |
| ADR-10 | 检查历史 `task_reviews` 只追加 | 在接收记录上覆盖最后结果 | 保留邀约、通过、退回的完整轮次，便于追溯退回重提；覆盖式无法还原历史 |
| ADR-11 | 自建任务使用独立 `personal_tasks` | 复用 `tasks` 并标记类型 | 自建任务无日期、紧急程度、接收人与检查，独立表避免大量空字段和语义混淆 |
| ADR-12 | 公司展示内容使用独立表且不关联任务 | 存入 `tasks` 并用类型区分 | 展示内容不参与派发、统计、日历和数据地图，从数据层隔离，防止误用 |
| ADR-13 | 日历同一天任务绿色优先于日志红色 | 叠加或拆分两种颜色 | 单日只能有一种标记，绿色表示存在任务占用；`logs`/`tasks` 明细仍分别返回供日视图使用 |
| ADR-14 | 管理员不继承任务权限 | 管理员拥有全部权限 | 管理员职责限于用户/组织/角色/配置与日志统计只读，任务权限按对象归属限制 |

## 12. 非功能设计

### 12.1 安全性

- 密码不存明文，BCrypt 加盐。
- 服务端统一鉴权与数据过滤，前端不可信。
- 关键管理操作写审计日志。
- 连续登录失败锁定账号。
- 令牌使用 HTTPS 传输（生产），密钥通过环境变量注入。

### 12.2 性能

- 普通页面加载 ≤ 3 秒；日志列表查询 ≤ 2 秒；100 条内统计 ≤ 3 秒。
- 任务列表、数据地图与日历查询 ≤ 2 秒；日历单次范围限制 31 天，避免全量扫描。
- 关键表建索引（作者+日期、角色、组织、状态、派发人+创建时间、接收人+更新时间、接收人+检查状态、任务日期区间）。
- 分页限制 size ≤ 100，避免一次拉取全量。
- 派发列表的接收人汇总按 `task_id` 聚合，不逐条回查；数据地图对派发接收与自建任务分别分页后合并，避免跨表全量排序。

### 12.3 可靠性

- 提交等写操作使用事务，失败回滚，不出现虚假成功。
- 提交采用条件更新保证幂等，防重复提交。
- 定时任务幂等，重复执行不产生副作用。

### 12.4 隐私与易用性

- 点评对话仅作者与直接上级可见，服务端强制过滤。
- 敏感信息不外发。
- 移动端主要操作 ≤ 3 层页面；错误信息说明修复方式。

## 14. 测试设计

| 层级 | 工具 | 覆盖点 |
|---|---|---|
| 单元测试 | JUnit + Mockito | 服务层业务规则、状态流转、直接上级与直接下级解析、任务对象鉴权 |
| 集成测试 | Spring Boot Test + Testcontainers(PostgreSQL) | 数据库约束、Mapper、事务、定时任务幂等、任务唯一约束与条件更新 |
| API 契约测试 | RestAssured / Postman | 接口鉴权、参数校验、错误码、权限过滤、任务状态与日期边界 |
| 前端组件/控件测试 | Jest + React Testing Library；Flutter widget test | 页面渲染、表单校验、交互、导图原地编辑、日历视图切换 |
| 端到端测试 | Playwright（Web）、Appium（Android） | 登录→写日志→提交→查看→点评→统计闭环；派发→接收→进度→邀约→检查闭环 |
| 安全测试 | 手工 + 自动化 | 越权访问、密码存储、登录锁定、审计、任务多人隔离与管理员越权 |
| 性能测试 | 简单压测脚本 | 页面/接口响应时间、99% 成功率、任务列表与日历查询 |

重点测试用例：

- 每人每天仅一条（重复创建返回 40901）。
- 提交后不可修改（返回 40902）。
- 员工只能看自己、团队长只能看本团队、部门老总只能看本部门。
- 点评对话隐私：同团队其他成员、更上级均不可见。
- 截止自动处理：有草稿自动提交、无草稿记为未提交、截止后禁止补交。
- 管理员日志只读，不可修改/删除。

任务专项测试用例：

- 派发范围：创始人只能派发部门老总、部门老总只能派发本部门团队长、团队长只能派发本团队员工；员工与管理员派发返回 403 `40310`。
- 派发校验：接收人为空、重复、停用账号返回 400 `40003`/`40310`；`startDate > deadline`、空名称/详情、非法紧急程度返回 400 `40002`；任一接收人不合法时整单回滚，不产生部分数据。
- 多人隔离：同一任务派发给 A、B 后，A 更新进度、完成邀约、被退回均不影响 B 的执行状态与检查状态；A 不能读取或操作 B 的接收记录（403 `40311`/`40312`）。
- 状态机：非法进度转换返回 409 `40910`；`PENDING`/`APPROVED` 下修改进度被拒绝；未完成即邀约返回 409 `40910`；重复邀约返回 409 `40911`；重复检查或已通过再检查返回 409 `40912`。
- 越权：非派发人调用检查返回 403 `40313`；非接收人调用进度/邀约返回 403 `40312`；管理员调用任一任务接口返回 403 `40310`。
- 退回重提：退回后执行状态回到 `IN_PROGRESS`、检查状态为 `RETURNED`，接收人可再次更新并邀约，`task_reviews` 保留 INVITED/APPROVED/RETURNED 全量历史。
- 日期边界：`startDate = deadline` 的单日任务在日历中只占一天；`startDate <= to AND deadline >= from` 相交判断包含开始日与截止日；超出 31 天的日历请求返回参数校验失败。
- 数据地图空值：自建任务返回 `source=PERSONAL` 且 `deadline`、`urgency`、`reviewStatus` 为 `null`，前端留空不报错；数据地图不返回本人派发给他人的任务。
- 公司内容排除：公司十大重要事项与公司十大重要任务不出现在派发、接收、数据地图、日历与统计结果中；非发布者调用维护接口返回 403 `40314`。
- 日志回归：新增任务能力后，日志创建/提交/截止处理、点评隐私、日志统计口径与管理员只读行为保持不变。
- 未定义生命周期（任务撤销/删除、增删接收人、检查通过后重新开启）不纳入本期用例，作为后续确认项跟踪。

## 15. 风险与待确认项

| 类别 | 风险/待确认 | 影响 | 应对 |
|---|---|---|---|
| 时区 | 服务端/数据库/定时任务时区不一致 | 截止处理错乱 | 统一 `Asia/Shanghai`，环境变量 `TZ` 与 DB 时区对齐 |
| 截止边界 | 21:59:59 与 22:00:00 的临界判定 | 提交/补交争议 | 明确「22:00 之后禁止」，定时任务按分钟幂等处理 |
| 组织删除 | 存在成员时删除部门/团队 | 数据悬挂 | 外键 `RESTRICT`，提示先迁移成员 |
| 创始人点评 | 创始人无上级，日志不可点评 | 需求理解偏差 | 按需求实现，验收时确认 |
| 重点事项 | 「标记重要」归属与权限 | 范围不清 | 设计为直接上级对下级日志标记，P1 可选 |
| 任务越权 | 仅按角色判断而忽略对象归属 | 可查看/操作他人任务 | 服务端同时校验权限码与 `sender_id`/`assignee_id`；管理员不继承任务权限 |
| 多人并发 | 同一接收记录被重复检查或并发改进度 | 状态被覆盖 | 条件更新 + 影响行数判断，冲突返回 409；`(task_id, assignee_id)` 唯一约束 |
| 组织调整 | 在途任务在人员调岗/停用后的归属未定义 | 接收人无法继续处理 | 本期保持原归属，列入待确认项，不新增迁移规则 |
| 任务生命周期 | 撤销/删除任务、增删接收人、通过后重新开启未定义 | 需求蔓延或误实现 | 本期不提供上述能力，列为后续确认项 |
| 日历语义 | 用户将绿色误解为任务进度或紧急程度 | 验收偏差 | 文档与界面注明颜色仅表示日期占用；`urgency` 不参与颜色 |
| 生产部署 | Nginx/腾讯云后置 | 上线延期 | 本期容器运行，部署项后置 |
| 范围容量 | 新增任务、公司展示与日历能力带来额外工作量 | Sprint 延期 | 在项目计划中标注容量复核风险，保持原里程碑日期不变 |

## 16. 附录

### 16.1 角色数据范围速查

| 角色 | 日志可见范围 | 点评权限 | 任务能力 | 管理权限 |
|---|---|---|---|---|
| 员工 | 自己 | 被点评/回复 | 接收任务、更新本人进度、邀约、自建任务 | 无 |
| 团队长 | 本团队 | 点评直接下级 | 向本团队员工派发与检查；接收、自建任务 | 无 |
| 部门老总 | 本部门 | 点评团队长 | 向本部门团队长派发与检查；接收、自建任务 | 无 |
| 创始人 | 全公司 | 点评部门老总 | 向部门老总派发与检查；接收、自建任务；维护公司十大重要任务 | 无 |
| 系统管理员 | 全公司（只读） | 无 | 只读公司展示内容，不可查看或操作他人任务 | 用户/组织/角色/配置/审计；维护公司十大重要事项 |

### 16.2 日志状态速查

| 状态 | 可编辑 | 可提交 | 可点评 |
|---|---|---|---|
| 草稿 DRAFT | 是（截止前） | 是（截止前） | 不可（未提交） |
| 已提交 SUBMITTED | 否 | 否（幂等） | 是 |
| 未提交（推导） | 否 | 否 | 不可 |

### 16.3 任务状态速查

| 执行状态 | 检查状态 | 可更新进度 | 可邀约 | 可检查 |
|---|---|---|---|---|
| `NOT_STARTED` | `NONE` | 是（→`IN_PROGRESS`） | 否 | 否 |
| `IN_PROGRESS` | `NONE`/`RETURNED` | 是（→`COMPLETED`） | 否 | 否 |
| `COMPLETED` | `NONE`/`RETURNED` | 否 | 是 | 否 |
| `COMPLETED` | `PENDING` | 否 | 否（409 `40911`） | 是（通过/退回） |
| `COMPLETED` | `APPROVED` | 否 | 否（409 `40912`） | 否 |
| `IN_PROGRESS` | `RETURNED` | 是 | 否（需先完成） | 否 |
