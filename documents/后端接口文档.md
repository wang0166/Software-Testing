# Pandora 后端 REST API 接口文档

> 版本：MVP 草案（依据 `documents/产品需求文档.md`、`documents/顶层设计文档.md`、`documents/技术设计文档.md` 编制）  
> Base URL：`/api`（本地默认 `http://localhost:8080/api`）  
> 适用端：Flutter Android、React 管理端、QA API 契约测试

> 实现状态说明：本文描述目标接口契约，不代表接口全部已实现。Web 管理端联调缺口与后端待办见第 15 节。

## 1. 范围与约定

本接口覆盖登录认证、用户与组织管理、工作日志、直属上级点评、任务派发与接收、逐接收人检查、自建任务、公司展示内容、日历与数据地图、统计、系统配置和审计查询。AI 摘要、通知、离线填报、数据导出不属于本期。

除登录、刷新令牌、退出登录及第 16 节的公开密码找回接口外，接口均须携带 `Authorization: Bearer <accessToken>`。请求和响应使用 UTF-8 JSON；日期使用 `YYYY-MM-DD`，时间戳使用 ISO-8601，业务时区统一为 `Asia/Shanghai`。服务端从令牌识别当前用户，任何 `authorId`、`teamId`、`departmentId` 查询条件都不能扩大服务端计算出的可见范围。

### 1.1 统一响应

成功响应：

```json
{"code":0,"message":"ok","data":{}}
```

分页列表的 `data`：

```json
{"items":[],"page":1,"size":20,"total":0}
```

错误响应：

```json
{"code":40301,"message":"无权访问该日志","data":null}
```

HTTP 状态码表达协议层结果（400/401/403/404/409/422/429/500）；`code` 是稳定的业务错误码。字段校验错误可在 `data.errors` 中返回字段到错误信息的映射。服务端不得向客户端返回密码哈希、刷新令牌哈希或内部异常堆栈。

### 1.2 身份与数据范围

| 身份 | 日志范围 | 点评关系 | 任务能力 | 管理能力 |
|---|---|---|---|---|
| `EMPLOYEE` | 自己 | 回复直属上级 | 接收任务、更新本人进度、邀约检查、自建任务、只读公司展示内容 | 无 |
| `TEAM_LEADER` | 所属团队 | 点评团队成员 | 向本团队员工派发并检查、接收任务、自建任务、只读公司展示内容 | 无 |
| `DEPT_MANAGER` | 所属部门 | 点评团队负责人 | 向本部门团队长派发并检查、接收任务、自建任务、只读公司展示内容 | 无 |
| `FOUNDER` | 全公司 | 点评部门负责人 | 向部门老总派发并检查、接收任务、自建任务、维护公司十大重要任务 | 无 |
| `ADMIN` | 全公司只读 | 不参与点评 | 只读公司展示内容；不可查看或操作他人任务 | 用户、组织、角色权限、配置、审计、公司十大重要事项维护 |

一个用户只有一种角色。员工和团队负责人必须属于一个团队；部门负责人属于一个部门；创始人和系统管理员不属于团队或部门。管理员虽可读取全公司日志和统计，但不能写入或修改日志，其日志只读权限不扩展为任务、自建任务或数据地图的访问权限。

### 1.3 权限码

功能权限码与对象级鉴权共同生效：功能权限码决定能否进入某类接口，对象级鉴权再校验当前用户是否为任务派发人、接收人或展示内容发布者。

| 权限码 | 含义 | 默认角色 |
|---|---|---|
| `task:dispatch` | 查询直接下级、派发任务、编辑任务内容、查看派发列表、检查接收人 | `TEAM_LEADER`、`DEPT_MANAGER`、`FOUNDER` |
| `task:execute` | 查看本人接收任务、更新本人进度、发起检查邀约 | `EMPLOYEE`、`TEAM_LEADER`、`DEPT_MANAGER`、`FOUNDER` |
| `task:self` | 新增、查看、编辑本人自建任务 | `EMPLOYEE`、`TEAM_LEADER`、`DEPT_MANAGER`、`FOUNDER` |
| `content:read` | 读取公司十大重要事项与公司十大重要任务 | 全部角色 |
| `company-matter:manage` | 维护公司十大重要事项 | `ADMIN` |
| `company-task:manage` | 维护公司十大重要任务 | `FOUNDER` |

管理员不具备 `task:dispatch`、`task:execute`、`task:self`，因此不能访问任务派发、任务接收、自建任务和数据地图接口。

## 2. 认证

### `POST /auth/login`

登录，不需要令牌。

```json
{"username":"zhangsan","password":"secret"}
```

成功返回 `accessToken`、`refreshToken`、`tokenType`、`expiresIn` 和 `user`（`id`、`username`、`realName`、`role`、`departmentId`、`teamId`、`permissions`）。`permissions` 为服务端解析的权限码数组，与 `GET /auth/me` 返回一致，客户端可在登录后直接做功能开关。停用或锁定账号拒绝登录；连续失败按安全配置锁定，成功后清零失败次数。

### `POST /auth/refresh`

```json
{"refreshToken":"..."}
```

校验刷新令牌并返回新的访问令牌。令牌轮换策略需在实现前确定（见第 14 节）。

### `POST /auth/logout`

```json
{"refreshToken":"..."}
```

撤销该刷新令牌/会话，成功后重复调用应幂等。

### `GET /auth/me`

返回当前账号摘要、角色、组织归属和可用权限码。账号权限以服务端为准。

### 账号开通与状态

- 所有账号（含创始人、部门老总、团队长、员工、系统管理员）均由管理员通过第 3 节接口在 Web 端创建；系统不提供注册接口，也不提供任何自助注册入口。
- Android 端只提供账号密码登录，不提供注册、找回密码等自助开户路径；密码由管理员创建或重置。
- 管理员通过 `PATCH /users/{id}/status` 停用账号后，该账号的登录请求返回 `40104`，已签发的访问令牌在过期前按服务端校验结果拒绝使用；重新启用后恢复登录。
- 登录、刷新、登出和 `/auth/me` 的行为不因上述开户方式改变。

## 3. 用户、组织、角色与权限（管理员）

以下接口要求管理员身份及对应管理权限。用户、审计列表分页，最大 `size` 为 100；公司、部门和团队是组织选择元数据，GET 列表返回完整数组，不截断为第一页。事项保持分页。

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/users` | 按关键字、`role`、`status`、`departmentId`、`teamId` 筛选用户 |
| `POST` | `/users` | 创建账号并分配唯一角色及合法组织归属 |
| `GET` | `/users/{id}` | 用户详情（不含凭据） |
| `PUT` | `/users/{id}` | 编辑姓名、角色、组织归属等资料 |
| `PATCH` | `/users/{id}/status` | 启用/停用 |
| `PUT` | `/users/{id}/password` | 管理员重置密码 |
| `GET` | `/companies` | 返回完整公司元数据，用于确定真实公司 ID，包括尚无部门时 |
| `GET` | `/companies/{id}` | 查询公司信息 |
| `PUT` | `/companies/{id}` | 编辑公司资料 |
| `GET/POST` | `/departments` | 部门列表/创建 |
| `GET/PUT/DELETE` | `/departments/{id}` | 部门详情/编辑/删除 |
| `GET/POST` | `/teams` | 团队列表/创建 |
| `GET/PUT/DELETE` | `/teams/{id}` | 团队详情/编辑/删除 |
| `GET` | `/roles` | 角色列表 |
| `GET` | `/permissions` | 权限码清单 |
| `PUT` | `/roles/{code}/permissions` | 设置角色权限 |

创建用户请求模板（尖括号内容须替换）：`{"username":"example_user","phone":"<11位手机号>","password":"<初始密码>","realName":"<姓名>","role":"TEAM_LEADER","departmentId":3,"teamId":8}`。密码由后端使用 BCrypt 哈希存储。删除组织时若仍有成员或下级组织，拒绝删除并要求先迁移归属。

2026-10-29 Web 范围调整：取消角色权限配置页面，保留账号角色选择、认证返回的权限与服务端权限校验。本节保留的角色/权限管理接口不再作为本轮 Web 交付缺口。

团队人员查看复用 `GET /users?teamId=<稳定团队ID>&keyword=<姓名或账号>&page=1&size=5`，不新增专用端点。服务端按 `teamId` 筛选并分页，返回 `items/page/size/total`；成员包含该团队负责人及员工，列表记录保留 `departmentId`、`teamId`，不能按团队名称匹配或只在单页结果中筛选。响应须剔除密码和密码哈希。

### 3.1 手机号辅助开户与前端初始密码（2026-10-28 确认）

本节需求已在 2026-10-29 本地后端实现，并通过真实 PostgreSQL 与浏览器联调；服务器部署状态另行确认。新建用户需按下表传入手机号。

| 字段 | 创建时要求 | 后端处理与返回 |
|---|---|---|
| `username` | 必填。手机号先自动填入，也可手改为 3～20 位小写字母、数字或下划线 | 保存为独立登录账户名并检查唯一性；不得强制用 phone 覆盖管理员已确认的 username |
| `phone` | 新开户必填，11 位、以 1 开头的数字字符串 | V7 新增可空历史字段；新开户接收、保存并返回，手机号是联系方式，允许复用；唯一登录标识为 username |
| `password` | 必填，前端当前要求至少 6 位且不能全为空格；支持随机生成 16 位含大小写字母、数字、特殊字符的初始密码，也可由管理员填写 | 生产环境经 HTTPS 传入，后端独立校验后用 BCrypt 哈希写入 password_hash；不写明文密码列、不记录密码日志，不在创建、列表或详情响应中返回密码或哈希 |
| `realName/role/departmentId/teamId` | 沿用本节已有角色与归属约束 | 服务端独立校验，用户 ID 由服务端生成，不以手机号代替稳定 ID |
| `gender/idNumber` | 可选扩展资料，性别为男/女；身份证号为空或 18 位，末位可为 X | V7 持久化；仅管理员管理接口返回，认证摘要不返回，不写入审计正文 |

开户交互和兼容要求：

- 新建时输入或修正手机号，未手改的账户名跟随填入；一旦手改，后续手机号变化不再覆盖。点击“恢复手机号”才恢复自动填入；重新打开新增表单重置该状态。
- 账户名与手机号是两个独立字段；手机号不同于账户名时，登录使用最终确认的账户名。仍通过 `POST /auth/login` 的 `username/password` 登录，不新增短信登录流程。
- 已有 admin 等账号不自动迁移或重命名；本次前端不开放已有账户名、手机号的修改。日后如需改手机号或账户名，先确认唯一性、修改权限和兼容规则；不擅自变更登录标识。
- 前端生成密码仅在本次表单内暂存，默认遮蔽，可显式显示或复制，取消或保存后清除；演示模式不请求后端，也不保存或验证真实密码。
- `POST /users` 返回稳定的 `id`；`GET /users`、`GET /users/{id}` 返回手机号等资料及部门/团队 ID 和名称，不返回密码、哈希或会话版本。
- 密码至少 6 位、不能全为空格，UTF-8 编码最多 72 字节，原样 BCrypt 哈希，不 trim 密码。重复账号返回 409/40906。旧账号手机号保持空值，不自动重命名或补造资料。
- `PUT /users/{id}` 接收完整的 `realName/role/departmentId/teamId`，不开放账号、手机号、性别和身份证号的修改；管理请求含未知字段返回 400，避免静默丢弃后提示成功。
- 查询响应状态为 `ACTIVE/DISABLED/LOCKED`；Web 启停写入 `{"status":1}` / `{"status":0}`，筛选支持 `1/0` 或上述字符串。启用会清理失败次数和临时锁定。
- 密码重置、账号启停、资料/角色归属更新会递增内部会话版本并撤销刷新会话，旧访问令牌返回 40102；账号当前停用时返回 40104。重新启用不会恢复旧会话，至少保留一个启用管理员，违反时返回 40908。

### 3.2 角色归属与唯一性

角色与组织归属必须满足以下约束，`POST /users` 与 `PUT /users/{id}` 均在服务端校验：

| 角色 | `departmentId` | `teamId` | 说明 |
|---|---|---|---|
| `EMPLOYEE` | 必填 | 必填 | 属于一个部门下的一个团队 |
| `TEAM_LEADER` | 必填 | 必填 | 必须是 `teamId` 对应团队的负责人，且团队所属部门与 `departmentId` 一致 |
| `DEPT_MANAGER` | 必填 | 必须为空 | 一个部门只有一名部门老总，不属于任何团队 |
| `FOUNDER` | 必须为空 | 必须为空 | 一个公司只有一名创始人 |
| `ADMIN` | 必须为空 | 必须为空 | 系统管理员不属于任何部门或团队 |

- 每名用户只能有一个角色，不支持兼任。
- 一个公司只能有一名创始人、一个部门只能有一名部门老总、一个团队只能有一名团队长；创建、编辑用户或通过 `PUT /teams/{id}` 设置团队负责人时均需校验。
- 角色与组织归属组合不合法，或团队长与团队、部门关系不一致，返回 `40001`（参数校验失败），响应中说明具体冲突字段。
- 创始人、部门老总、团队长已存在时再指定同类负责人，返回 `40905`（组织负责人已存在）。
- 团队负责人变更时，原负责人不得继续以 `TEAM_LEADER` 身份保留在该团队，需在同一事务内调整其角色或归属。
- `PUT /teams/{id}` 可选传 `leaderId`，新负责人必须是本团队员工；同一事务内将旧负责人改为员工并提升新负责人。省略或传空不调整负责人；清空职务使用用户角色接口。公司创始人和部门负责人通过用户角色/归属接口同步，不直接写入组织指针。
- 上述约束不能只依赖前端限制，接口层必须独立校验。

## 4. 工作日志

日志对象字段：`id`、`authorId`、`logDate`、`content`、`status`（`DRAFT`/`SUBMITTED`）、`isImportant`、`submittedAt`、`createdAt`、`updatedAt`。日期由服务端按上海时区生成，客户端不得指定历史或未来日期。内容为非空自由文本。

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/logs` | 在当前角色可见范围内查询；可选 `date`、`status`、`authorId`、`page`、`size` |
| `GET` | `/logs/{id}` | 查询单篇日志，执行同等范围校验 |
| `POST` | `/logs` | 为当前用户创建当天草稿，body：`{"content":"..."}` |
| `PUT` | `/logs/{id}` | 作者在截止时间前编辑 `DRAFT` 内容 |
| `POST` | `/logs/{id}/submit` | 作者提交草稿；重复提交按幂等成功或 409（团队统一约定） |
| `POST` | `/logs/{id}/important` | 直属上级标记/取消重点，body：`{"isImportant":true}`（P1 可选） |

日志列表与详情额外返回 `authorRole/departmentId/departmentName/teamId/teamName`，无归属字段可为 null，供移动端分组及点评入口判断；读取范围与点评权限仍由服务端校验。

业务约束：每人每天最多一篇；内容不得为空；创建时服务端设置当天日期；提交后永久不可修改；截止时间默认 22:00，可由管理员配置。截止后禁止新建、编辑、提交。编辑和首次提交必须属于当天，不能次日补交旧草稿。截止任务每分钟幂等将到期草稿转为 `SUBMITTED`，重启后补处理历史草稿，`submittedAt` 记录实际处理时刻；当天无日志的人不落库，统计时推导为未提交。写操作使用事务并保证并发下唯一约束生效。

## 5. 点评对话

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/logs/{id}/comments` | 仅日志作者和作者的直属上级可读 |
| `POST` | `/logs/{id}/comments` | 直属上级发起、作者回复 |

请求：`{"content":"请补充风险项。","parentId":null}`。回复时 `parentId` 指向被回复的点评。发起人必须是该作者的直接上级；回复人必须为日志作者；其他团队成员、越级上级和管理员均不可查看或参与。评论内容不能为空。

## 6. 统计

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/stats/overview` | 应提交人数、已提交人数、提交率、未提交人数 |
| `GET` | `/stats/unsubmitted` | 当前范围未提交人员名单 |
| `GET` | `/stats/counts` | 日/周/月日志数量，参数 `from`、`to`、`groupBy` |
| `GET` | `/stats/trend` | 近 7/30 天趋势，参数 `days=7|30` |
| `GET` | `/stats/important` | 重点日志列表（P1，可选） |

当前用户统计范围与其日志读取范围一致。应提交人数为范围内需写日志的启用用户数（不含管理员）；已提交人数为当天存在 `SUBMITTED` 日志的用户数（含截止任务自动提交的草稿）；未提交人员为应提交用户中当天无已提交日志者；提交率 = 已提交人数 / 应提交人数，应提交人数为 0 时返回 0。

## 7. 任务：直接下级与派发

任务对象字段：`id`、`senderId`、`name`、`details`、`startDate`、`deadline`、`urgency`（`URGENT`/`NOT_URGENT`）、`createdAt`、`updatedAt`。任务内容由派发人维护，向一个或多个直接下级派发；每名接收人获得独立接收记录，进度与检查状态互不影响。

### 7.1 查询可派发的直接下级

`GET /tasks/recipients`

返回当前用户可派发的直接下级（仅启用账号）：

| 当前角色 | 直接下级范围 |
|---|---|
| `FOUNDER` | 全部启用状态的部门老总 |
| `DEPT_MANAGER` | 本部门启用状态的团队长 |
| `TEAM_LEADER` | 本团队启用状态的员工 |
| `EMPLOYEE`、`ADMIN` | 无，返回 403 `40310` |

```json
{"code":0,"message":"ok","data":{"items":[{"id":12,"realName":"李四","role":"TEAM_LEADER","departmentId":3,"teamId":8}]}}
```

### 7.2 派发任务

`POST /tasks`

```json
{
  "name":"完成10月经营分析",
  "details":"汇总各团队数据并输出报告",
  "startDate":"2026-10-20T09:30:00",
  "deadline":"2026-10-25T17:45:00",
  "urgency":"URGENT",
  "assigneeIds":[12,13]
}
```

校验规则：

- `name`、`details` 去空格后不得为空；`name` 最长 200 字符，`details` 为自由文本。
- `startDate`、`deadline` 使用北京时间 `YYYY-MM-DDTHH:mm:ss`（秒必须为 `00`，也可省略秒），且截止必须严格晚于开始。兼容旧纯日期请求：开始按 `00:00`、截止按 `23:59` 解释；新客户端使用分钟格式，不传 `Z` 或时区偏移。
- `urgency` 只能为 `URGENT` 或 `NOT_URGENT`。
- `assigneeIds` 至少一人、不得重复；每名接收人都必须是当前用户的直接下级且账号启用。
- 任一接收人不合法时整单拒绝，不创建部分任务或部分接收记录。
- 服务端在一个事务内创建一条共享任务内容和每名接收人一条接收记录；接收记录初始为 `executionStatus=NOT_STARTED`、`reviewStatus=NONE`。

成功返回：

```json
{"code":0,"message":"ok","data":{"taskId":501,"assigneeCount":2}}
```

字段校验失败返回 400 `40002`，接收人列表非法返回 400 `40003`，存在非直接下级返回 403 `40310`。

### 7.3 派发任务列表

`GET /tasks/dispatched?page=1&size=20`

仅返回当前用户派发的任务，按 `createdAt` 倒序。`data.items` 每项包含任务摘要与接收人汇总：

```json
{
  "id":501,
  "name":"完成10月经营分析",
  "startDate":"2026-10-20T09:30:00",
  "deadline":"2026-10-25T17:45:00",
  "urgency":"URGENT",
  "assigneeCount":2,
  "completedCount":1,
  "pendingReviewCount":1,
  "createdAt":"2026-10-18T09:30:00+08:00"
}
```

`completedCount` 统计 `executionStatus=COMPLETED` 的接收记录数，`pendingReviewCount` 统计 `reviewStatus=PENDING` 的接收记录数；汇总只用于列表展示，不改变逐接收人状态。

### 7.4 派发任务详情

`GET /tasks/{taskId}`

仅任务派发人可访问，返回共享任务内容和全部接收记录：

```json
{
  "id":501,
  "name":"完成10月经营分析",
  "details":"汇总各团队数据并输出报告",
  "startDate":"2026-10-20T09:30:00",
  "deadline":"2026-10-25T17:45:00",
  "urgency":"URGENT",
  "assignments":[
    {"assignmentId":9101,"assignee":{"id":12,"realName":"李四"},"executionStatus":"COMPLETED","reviewStatus":"PENDING","updatedAt":"2026-10-24T18:00:00+08:00"},
    {"assignmentId":9102,"assignee":{"id":13,"realName":"王五"},"executionStatus":"IN_PROGRESS","reviewStatus":"NONE","updatedAt":"2026-10-23T10:00:00+08:00"}
  ]
}
```

非派发人访问返回 403 `40311`；任务不存在或不可见返回 404 `40410`。

### 7.5 编辑任务内容

`PUT /tasks/{taskId}`

仅任务派发人可调用，请求体为 `name`、`details`、`startDate`、`deadline`、`urgency`，校验规则同派发。编辑只修改共享任务内容，不改变任何接收人的执行状态或检查状态。当前版本不提供增删接收人。

成功返回更新后的任务内容；非派发人返回 403 `40311`，状态冲突不适用于本接口。

## 8. 任务接收、进度与检查

### 8.1 状态枚举

| 枚举 | 取值 | 说明 |
|---|---|---|
| 执行状态 `executionStatus` | `NOT_STARTED`、`IN_PROGRESS`、`COMPLETED` | 仅接收人可更新本人记录 |
| 检查状态 `reviewStatus` | `NONE`、`PENDING`、`APPROVED`、`RETURNED` | `PENDING` 表示已邀约待派发人检查 |
| 紧急程度 `urgency` | `URGENT`、`NOT_URGENT` | 任务内容字段，不参与日历颜色 |
| 检查动作 `action` | `INVITED`、`APPROVED`、`RETURNED` | 写入检查历史 |

允许的执行进度转换：`NOT_STARTED → IN_PROGRESS`、`IN_PROGRESS → COMPLETED`。相同状态重复提交按幂等成功处理；其他转换返回 409 `40910`。当 `reviewStatus` 为 `PENDING` 或 `APPROVED` 时禁止修改进度。

### 8.2 本人接收任务列表

`GET /tasks/received?status=IN_PROGRESS&reviewStatus=PENDING&page=1&size=20`

仅返回当前用户的接收记录，`status` 按执行状态筛选，`reviewStatus` 按检查状态筛选，二者均可选。每项包含：

```json
{
  "assignmentId":9101,
  "taskId":501,
  "name":"完成10月经营分析",
  "details":"汇总各团队数据并输出报告",
  "startDate":"2026-10-20T09:30:00",
  "deadline":"2026-10-25T17:45:00",
  "urgency":"URGENT",
  "executionStatus":"COMPLETED",
  "reviewStatus":"PENDING",
  "sender":{"id":9,"realName":"赵六"},
  "updatedAt":"2026-10-24T18:00:00+08:00"
}
```

### 8.3 接收任务详情

`GET /tasks/assignments/{assignmentId}`

仅该接收记录的接收人可访问，返回任务内容、本人执行状态、检查状态和检查历史；检查历史按时间正序：

```json
{
  "assignmentId":9101,
  "taskId":501,
  "name":"完成10月经营分析",
  "details":"汇总各团队数据并输出报告",
  "startDate":"2026-10-20T09:30:00",
  "deadline":"2026-10-25T17:45:00",
  "urgency":"URGENT",
  "executionStatus":"COMPLETED",
  "reviewStatus":"PENDING",
  "sender":{"id":9,"realName":"赵六"},
  "reviews":[
    {"action":"INVITED","actorId":12,"comment":null,"createdAt":"2026-10-24T18:00:00+08:00"}
  ]
}
```

非本人接收记录返回 403 `40311`；不存在或不可见返回 404 `40410`。

### 8.4 更新本人进度

`PATCH /tasks/assignments/{assignmentId}/progress`

```json
{"status":"IN_PROGRESS"}
```

仅接收人可操作，目标状态只能为 `NOT_STARTED`、`IN_PROGRESS`、`COMPLETED`。服务端使用条件更新校验当前状态和 `reviewStatus`，并发重复请求只有一个生效，其余按幂等成功或 409 `40910` 返回。非接收人操作返回 403 `40312`。

### 8.5 发起检查邀约

`POST /tasks/assignments/{assignmentId}/review-invitations`

仅接收人可调用；要求本人 `executionStatus=COMPLETED` 且 `reviewStatus` 为 `NONE` 或 `RETURNED`。成功后 `reviewStatus` 置为 `PENDING`，并写入一条 `task_reviews(action=INVITED)`。

- 未完成时调用返回 409 `40910`。
- 已处于 `PENDING` 返回 409 `40911`。
- 已 `APPROVED` 返回 409 `40912`。
- 非接收人调用返回 403 `40312`。

### 8.6 派发人检查

`POST /tasks/assignments/{assignmentId}/review`

```json
{"result":"APPROVED","comment":"数据准确，通过"}
```

仅任务派发人可调用，要求该接收记录 `reviewStatus=PENDING`：

- `result=APPROVED`：检查状态置为 `APPROVED`，执行状态保持 `COMPLETED`。
- `result=RETURNED`：检查状态置为 `RETURNED`，执行状态回到 `IN_PROGRESS`，接收人可继续修改后再次邀约。
- 每次检查追加一条 `task_reviews`，`action` 分别为 `APPROVED` 或 `RETURNED`，`comment` 可为空。
- 使用条件更新（`reviewStatus=PENDING`）保证并发下只有一个检查请求生效，其余返回 409 `40912`。
- 非派发人返回 403 `40313`；接收记录不属于该任务派发人的任务时同样拒绝。

### 8.7 双接收人隔离示例

任务 501 同时派发给用户 12 和 13，对应接收记录 9101、9102：

1. 用户 12 更新进度为 `IN_PROGRESS`，9101 变为 `IN_PROGRESS/NONE`，9102 仍为 `NOT_STARTED/NONE`。
2. 用户 12 完成并邀约检查，9101 变为 `COMPLETED/PENDING`，9102 不受影响。
3. 派发人通过 9101，9101 变为 `COMPLETED/APPROVED`；9102 仍为 `NOT_STARTED/NONE`。
4. 派发人退回 9102 前，9102 必须已由用户 13 完成并邀约；退回只把 9102 恢复为 `IN_PROGRESS/RETURNED`，不改变 9101。

## 9. 自建任务与公司展示内容

三类记录相互分离：自建任务属于个人，公司十大重要事项与公司十大重要任务属于独立展示内容，均不生成常规任务或接收记录，不进入任务派发、统计、数据地图或日历。

### 9.1 自建任务

自建任务字段：`id`、`ownerId`、`name`、`details`、`status`（`NOT_STARTED`/`IN_PROGRESS`/`COMPLETED`）、`createdAt`、`updatedAt`；不包含日期、紧急程度和检查状态。

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/personal-tasks` | 查询本人自建任务，分页，按 `updatedAt` 倒序 |
| `POST` | `/personal-tasks` | 新增，body：`{"name":"...","details":"...","status":"NOT_STARTED"}`，`status` 可省略并默认 `NOT_STARTED` |
| `PUT` | `/personal-tasks/{id}` | 编辑本人任务的名称、详情和状态 |

仅创建者本人可查看和编辑；其他用户（含管理员）访问返回 403 `40311` 或 404 `40410`。名称、详情不得为空，状态只能取上述三值。

### 9.2 公司十大重要事项

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/company-matters` | 所有已登录用户只读，按 `sortOrder`、`id` 排序 |
| `POST` | `/company-matters` | 仅管理员，权限码 `company-matter:manage` |
| `PUT` | `/company-matters/{id}` | 仅管理员，编辑标题、内容、排序与起止时间 |

字段为 `id`、`title`、`content`、`sortOrder`、`startDate`、`deadline`、`updatedAt`。`title`、`content` 不得为空，排序为整数。当前版本不定义删除接口。

2026-10-29 已实现并验证事项起止时间约定（精确到小时）：

- 公司十大事项移到 Web 左侧独立菜单；创建与编辑保留 `startDate`、`deadline` 字段名，内容由纯日期调整为带 `+08:00` 的整点 ISO-8601 时间戳，例如 `2026-10-29T09:00:00+08:00`。两者必填，使用 `Asia/Shanghai`，小时为 `00～23`，分钟和秒均为 `00`，Web 不提供分钟选择。
- `deadline >= startDate`，允许同一整点，也允许跨日；前后端均须拒绝非法日期、非整点和倒序范围，不能只比较日期部分。
- 后端须增加可保留小时的数据库时间字段、DTO/服务/映射支持，并在查询结果按上述格式返回；不能继续使用纯 DATE 字段而丢失小时。历史记录允许未补录，返回空值或缺省时显示“未设置”；旧纯日期仍按日期展示，编辑保存前必须补选小时，不擅自解释为零点或用当前时间代填。
- GET 已返回起止时间，POST/PUT 已实现，V7 使用 TIMESTAMPTZ 保存。历史记录的两个时间可同时为空，不推断小时；新建与编辑 API 均必填。该约定仅扩展公司重要事项，不自动扩展下节“公司十大重要任务”。

请求示例：`{"title":"项目验收","content":"完成前后端验收","sortOrder":1,"startDate":"2026-10-29T09:00:00+08:00","deadline":"2026-11-05T18:00:00+08:00"}`。

### 9.3 公司十大重要任务

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/company-important-tasks` | 所有已登录用户只读，按 `sortOrder`、`id` 排序 |
| `POST` | `/company-important-tasks` | 仅创始人，权限码 `company-task:manage` |
| `PUT` | `/company-important-tasks/{id}` | 仅创始人，编辑标题、内容与排序 |

本类仍使用 `id/title/content/sortOrder/updatedAt`，标题和内容不得为空；本轮不扩展起止日期。非对应发布者调用维护接口返回 403 `40314`；“十大”仅为展示名称，接口不设置硬性条数上限。

## 10. 数据地图与日历读取

### 10.1 数据地图

`GET /task-map?page=1&size=20`

只读聚合当前用户收到的派发任务和本人自建任务，不返回本人派发给他人的任务，也不返回公司展示内容。每项包含：

```json
{
  "source":"DISPATCHED",
  "taskId":501,
  "assignmentId":9101,
  "personalTaskId":null,
  "name":"完成10月经营分析",
  "deadline":"2026-10-25T17:45:00",
  "urgency":"URGENT",
  "executionStatus":"IN_PROGRESS",
  "reviewStatus":"NONE"
}
```

- `source` 取 `DISPATCHED` 或 `PERSONAL`。
- 自建任务返回 `source=PERSONAL`、`taskId=null`、`assignmentId=null`、`personalTaskId` 有值；`deadline`、`urgency`、`reviewStatus` 返回 `null`，前端对应列留空。
- 数据地图不提供写接口；内容或状态变更必须通过任务接收、派发任务或自建任务接口完成，再次读取时反映最新数据。
- 管理员不具备 `task:execute`/`task:self`，调用返回 403 `40310`。

### 10.2 日历

`GET /calendar?from=2026-10-01&to=2026-10-31`

`from`、`to` 必填且为 `YYYY-MM-DD`，要求 `from <= to`，范围最长 31 天。返回按日期升序的 `days`：

```json
{
  "days":[
    {"date":"2026-10-20","logCount":0,"taskCount":1,"mark":"GREEN","logs":[],"tasks":[{"taskId":501,"assignmentId":9101,"name":"完成10月经营分析","executionStatus":"IN_PROGRESS","reviewStatus":"NONE"}]},
    {"date":"2026-10-21","logCount":1,"taskCount":0,"mark":"RED","logs":[{"logId":88,"authorId":12,"status":"SUBMITTED"}],"tasks":[]},
    {"date":"2026-10-22","logCount":1,"taskCount":1,"mark":"GREEN","logs":[{"logId":89,"authorId":12,"status":"SUBMITTED"}],"tasks":[{"taskId":501,"assignmentId":9101,"name":"完成10月经营分析","executionStatus":"IN_PROGRESS","reviewStatus":"NONE"}]}
  ]
}
```

- 日志按当前用户既有日志可见范围读取，只返回 `logDate` 落在范围内的日志。
- 任务只读取当前用户的接收记录，日期相交条件为 `startDate <= to AND deadline >= from`，包含开始日和截止日。
- `mark` 取 `GREEN`、`RED`、`NONE`；同一天同时存在日志和任务时只返回 `GREEN`，但 `logs` 与 `tasks` 仍分别返回供日视图使用。
- 自建任务和公司展示内容不参与日历；颜色只表示日期占用，不表达任务进度或紧急程度。
- 管理员不可调用日历任务读取；调用返回 403 `40310`。

## 13. 安全、并发与审计要求

- 密码仅以 BCrypt 哈希保存；生产环境只经 HTTPS 传输；JWT 密钥通过环境变量注入。
- 认证、角色权限与数据范围在服务端统一执行；高风险越权不得只依赖前端隐藏页面。
- 公司创始人、部门老总和团队长的唯一性由数据库唯一索引兜底（`companies.founder_id`、`departments.manager_id`、`teams.leader_id`），并发写入冲突转换为 `40905`。
- 角色与组织归属的一致性由服务端校验，覆盖创建用户、编辑用户和设置团队负责人三条路径：单表内的角色-归属组合由 `users` 表 CHECK 约束保证，团队长与团队、部门的一致性由服务层跨表校验，不满足时返回 `40001`。
- 账号只能由管理员创建，不提供注册接口；账号启停与组织负责人变更必须写审计日志。
- 日志日唯一键由数据库约束保障；提交使用条件更新或等效并发控制；截止任务必须幂等。
- 任务接收记录以 `(task_id, assignee_id)` 唯一约束防止重复派发；进度、邀约和检查均使用带当前状态条件的更新，避免多人并发串改进度。
- 任务权限同时校验功能权限码和对象归属：派发人只能操作自己派发的任务，接收人只能操作自己的接收记录，管理员不得访问他人任务。
- 公司展示内容的维护接口只允许对应发布者调用，展示内容不得写入 `tasks` 或 `task_assignments`。
- 登录失败次数/锁定、账号启停、用户与组织变更、角色权限与配置变更写审计日志。

## 16. 新移动端对接与密码审批（2026-10-29）

本轮新增 V8（任务分钟精度、密码申请与限流存储），V1～V7 原迁移不修改。具体字段、管理员审核请求、一次性恢复凭据交付、错误码、迁移与验收见 [移动端新版后端对接与验收](移动端新版后端对接与验收.md)。本文已有的目标接口不能据此视为全部实现。

| 方法 | 接口 | 权限 |
|---|---|---|
| POST | `/auth/password-reset-requests` | 公开，统一受理提示；仅创建申请，不凭账号直接改密 |
| POST | `/account/password-change-requests` | 本人登录，创建待审核申请 |
| GET | `/account/password-change-requests/me` | 本人登录，查询 NONE/PENDING/APPROVED/REJECTED |
| POST | `/account/password-change` | 本人登录且有有效批准；body 为 newPassword |
| GET | `/password-requests` | 管理员且有 user:manage，分页查询申请，不返回凭据 |
| POST | `/password-requests/{id}/review` | 管理员重新验证密码及核验申请人，不允许自审 |
| POST | `/auth/password-reset` | 公开，携带一次性 token 与本人设置的 newPassword |

申请有效期 24 小时；批准后 15 分钟有效。新密码至少 8 位，UTF-8 不超过 72 字节；原开户/管理员直接重置的 6 位下限保留。改密成功撤销全部旧访问及刷新会话，移动端必须重新登录。忘记密码未接邮件/短信，恢复凭据由管理员完成身份核验后通过受控渠道交给本人，不能宣称已自动发送；Web 审批页面与移动端找回凭据输入页未包含在此次后端修改中。

新增错误：HTTP 409/40920（重复、过期或已处理申请），403/40320（缺少有效批准），400/40020（恢复凭据无效或过期），429/42901（请求过频）。公开找回申请对不存在/停用账号、重复申请及限流统一响应，不泄露账号状态。审核每管理员 15 分钟最多 20 次；公开申请及恢复完成按账号/凭据 5 次、来源地址 30 次，计数由共享数据库保存。
