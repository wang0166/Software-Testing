# 顶层设计文档 —— 智能掌上日志系统（潘多拉 Pandora）

## 1. 文档说明

本文档描述「智能掌上日志系统（潘多拉 Pandora）」的顶层设计，包括总体架构、技术选型、系统分层、数据模型、权限设计、关键流程、部署架构和迭代分工，与《产品需求文档》配套使用。

## 2. 总体架构

系统采用前后端分离的三层架构：

```text
┌────────────────────┐   ┌────────────────────┐
│  Flutter Android 端 │   │  React Web 管理端   │
│ 员工/团队长/部门老总 │   │ 系统管理员          │
│ /创始人             │   │                    │
└─────────┬──────────┘   └─────────┬──────────┘
          │                        │
          └──────────┬─────────────┘
                     ▼
         ┌─────────────────────┐
         │   Java Spring 后端    │
         │ 认证/用户/组织/角色/   │
         │ 日志/点评/统计/配置    │
         └──────────┬──────────┘
                     ▼
         ┌─────────────────────┐
         │     PostgreSQL      │
         └─────────────────────┘
```

Android 端供除管理员外的所有角色使用；Web 端仅供管理员使用。所有客户端通过后端 RESTful API 访问数据，数据权限由后端统一强制校验。

## 3. 技术选型

| 层面 | 选型 |
|---|---|
| 移动客户端 | Flutter（Dart） |
| Web 管理端 | React + JavaScript |
| 后端 | Java + Spring Boot |
| 数据持久层 | MyBatis |
| 数据库 | PostgreSQL |
| 构建工具 | Maven |
| 容器化 | Docker |
| 反向代理 | Nginx（服务器暂定腾讯云，现阶段先不实现） |
| 消息队列 | 不需要（并发量很小） |

## 4. 系统分层与模块

### 4.1 分层

- 表现层：Flutter App、React Web 管理端。
- 应用/业务层：认证、用户、组织、角色权限、日志、点评、统计、系统配置、审计。
- 数据层：PostgreSQL。

### 4.2 核心模块

| 模块 | 职责 |
|---|---|
| 认证模块 | 登录、登出、会话/令牌管理 |
| 用户模块 | 用户信息、账号状态 |
| 组织模块 | 公司、部门、团队结构维护 |
| 角色权限模块 | 角色与权限，服务端数据过滤 |
| 日志模块 | 草稿、提交、截止自动处理、状态流转 |
| 点评模块 | 直接上级点评、下级回复、可见性控制 |
| 统计模块 | 提交率、未提交名单、日志数量、趋势、重点事项 |
| 系统配置模块 | 截止时间等参数 |
| 审计模块 | 管理员操作记录 |

## 5. 核心数据模型

### 5.1 组织与用户

| 表 | 主要字段 |
|---|---|
| companies | 公司 ID、名称（单公司） |
| departments | 部门 ID、名称、公司 ID、部门老总 ID |
| teams | 团队 ID、名称、部门 ID、团队长 ID |
| users | 用户 ID、账号、密码摘要、姓名、角色、部门 ID、团队 ID、状态、创建时间 |

### 5.2 角色与权限

角色采用固定枚举：员工、团队长、部门老总、创始人、系统管理员。权限主要体现为数据可见范围和功能开关：

| 角色 | 日志可见范围 | 点评权限 | 管理权限 |
|---|---|---|---|
| 员工 | 自己 | 被点评/回复 | 无 |
| 团队长 | 本团队 | 点评直接下级 | 无 |
| 部门老总 | 本部门 | 点评直接下级（团队长） | 无 |
| 创始人 | 全公司 | 点评直接下级（部门老总） | 无 |
| 系统管理员 | 全公司（只读） | 无 | 用户/组织/角色/权限/配置 |

### 5.3 日志与点评

| 表 | 主要字段 |
|---|---|
| work_logs | 日志 ID、作者 ID、日志日期、内容、状态、提交时间、创建/更新时间 |
| log_comments | 评论 ID、日志 ID、评论人 ID、内容、父评论 ID、创建时间 |

日志状态：草稿、已提交。未提交用户不落 work_logs 记录，或通过统计维度区分（建议由「当日无记录且已过截止时间」判定）。

### 5.4 统计与审计

| 表 | 主要字段 |
|---|---|
| system_configs | 配置项、配置值（如截止时间） |
| operation_audits | 操作人、操作类型、对象、时间、结果 |

统计指标可基于 work_logs 实时计算，规模较小时不必预聚合。

## 6. 权限与可见性设计

### 6.1 日志可见规则

服务端在查询日志时按当前用户角色和归属强制拼接过滤条件：

- 员工：author_id = 自己。
- 团队长：author 所在团队 = 自己的团队。
- 部门老总：author 所在部门 = 自己的部门。
- 创始人：无过滤，全公司。
- 系统管理员：无过滤（只读）。

### 6.2 点评可见规则

点评对话仅对「作者 + 作者的直接上级」开放。服务端查询评论时：

- 允许：评论作者、日志作者、日志作者的直接上级。
- 拒绝：同团队/同部门其他成员，以及更上级（如部门老总看团队长点评员工）。

### 6.3 管理员权限

- 可读：所有用户、组织、日志、统计。
- 可写：用户、组织、角色、权限、系统配置。
- 不可写：日志内容（不可修改或删除）。

## 7. 关键业务流程

### 7.1 日志状态流转

```text
新建日志（内容非空）
      │
      ▼
   草稿 ──编辑──▶ 草稿
      │
      ├── 正式提交 ──▶ 已提交（不可修改）
      │
      └── 到截止时间（有草稿）──▶ 自动作为当日日志（已提交）

截止时间（无草稿）──▶ 未提交（不可补交）
```

### 7.2 点评流程

```text
员工提交日志
      │
      ▼
团队长（直接上级）发起点评
      │
      ▼
员工回复 → 形成对话
      │
      └─ 仅员工与团队长可见
```

### 7.3 登录流程

```text
账号密码 → 服务端校验 → 返回令牌 → 客户端按角色加载对应界面
```

## 8. 接口设计概要

| 分组 | 主要接口 |
|---|---|
| 认证 | 登录、登出、刷新令牌 |
| 用户 | 创建、查询、编辑、停用/启用 |
| 组织 | 公司/部门/团队的增删改查 |
| 日志 | 新建、保存草稿、提交、查询详情、列表 |
| 点评 | 发起点评、回复、查询对话 |
| 统计 | 个人/团队/部门/公司统计 |
| 配置 | 读取/修改系统参数 |
| 审计 | 查询操作记录 |

所有接口统一鉴权，并在服务端按第 6 节规则做数据权限过滤。

## 9. 部署架构

```text
┌────────────┐
│   Nginx    │  （反向代理，暂定腾讯云，现阶段本地/容器即可）
└─────┬──────┘
      │
 ┌────┴─────┐        ┌──────────────┐
 │ React Web │        │ Spring Boot   │
 └──────────┘        │ 后端服务       │
                      └──────┬───────┘
                             │
                      ┌──────▼───────┐
                      │ PostgreSQL    │
                      └──────────────┘
```

使用 Docker 容器化，建议以 docker-compose 编排 Web、后端和数据库。本期先实现本地或容器运行，腾讯云与 Nginx 生产部署后置。

## 10. 迭代与分工建议

### 10.1 Sprint 规划

| Sprint | 目标 | 主要交付 |
|---|---|---|
| Sprint 0 | 需求与设计 | 需求文档、顶层设计、数据模型、接口契约、OpenSpec 初始化 |
| Sprint 1 | 首条闭环 | 登录 → 新建日志 → 草稿 → 提交 → 落库 |
| Sprint 2 | 核心功能 | 按角色查看日志、点评对话、统计、管理端 |
| Sprint 3 | 测试与发布 | 截止自动处理、权限校验、非功能测试、部署演示 |
| Final | 验收展示 | 完整系统、测试报告、演示材料 |

### 10.2 五人分工总览

| 成员 | 建议角色 | 主要负责 |
|---|---|---|
| A | 产品/需求 | 需求文档、用户故事、验收标准、原型、Backlog |
| B | Android 端 | Flutter 日志、登录、草稿、提交、个人统计 |
| C | Web 端 | React 管理端、用户/组织/角色/权限/配置、只读日志与统计 |
| D | 后端与数据 | Spring Boot、MyBatis、PostgreSQL、接口与权限校验 |
| E | 测试与工程质量 | 测试计划、端到端链路、非功能验证、Docker/CI |

### 10.3 协作要求

- 全员在 Git 平台使用独立分支，保留可核验提交记录。
- 后端先定接口契约，前端可先用 Mock 数据并行开发。
- 权限规则统一由后端定义，前端只负责展示和路由控制。
- 测试从 Sprint 0 开始介入，每个 Sprint 都执行测试。
- 不以「代码完成」代替「功能验收」，必须提供运行或测试证据。
