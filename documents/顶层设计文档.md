# 顶层设计文档 —— 智能掌上日志系统（潘多拉 Pandora）

## 1. 文档说明

本文档描述「智能掌上日志系统（潘多拉 Pandora）」的顶层设计，包括总体架构、技术选型、系统分层、数据模型、权限设计、关键流程、部署架构和迭代分工，与《产品需求文档》配套使用。

## 2. 总体架构

系统采用前后端分离的三层架构：

```text
┌────────────────────┐   ┌────────────────────┐
│  Flutter Android 端 │   │  React Web 管理端   │
│ 员工/团队长/部门老总 │   │ 系统管理员          │
│ /创始人             │   │                    │
└─────────┬──────────┘   └─────────┬──────────┘
          │                        │
          └──────────┬─────────────┘
                     ▼
         ┌─────────────────────┐
         │   Java Spring 后端    │
         │ 认证/用户/组织/角色/   │
         │ 日志/点评/任务/展示内容 │
         │ 统计/配置/审计/日历地图 │
         └──────────┬──────────┘
                     ▼
         ┌─────────────────────┐
         │     PostgreSQL      │
         └─────────────────────┘
```

Android 端供除管理员外的所有角色使用，承担日志、任务派发与接收、逐接收人检查、自建任务、公司重点展示内容查看及创始人维护公司十大重要任务；Web 端仅供管理员使用，承担用户/组织/角色/权限/配置管理、日志与统计只读查看，以及公司十大重要事项的发布与编辑。所有客户端通过后端 RESTful API 访问数据，数据权限由后端统一强制校验。

## 3. 技术选型

| 层面 | 选型 |
|---|---|
| 移动客户端 | Flutter（Dart） |
| Web 管理端 | React + JavaScript |
| 后端 | Java + Spring Boot |
| 数据持久层 | MyBatis |
| 数据库 | PostgreSQL |
| 构建工具 | Maven |
| 容器化 | Docker |
| 反向代理 | Nginx（服务器暂定腾讯云，现阶段先不实现） |
| 消息队列 | 不需要（并发量很小） |

## 4. 系统分层与模块

### 4.1 分层

- 表现层：Flutter App、React Web 管理端。
- 应用/业务层：认证、用户、组织、角色权限、日志、点评、任务派发与执行、公司重点展示内容、统计、系统配置、审计。
- 数据层：PostgreSQL。

### 4.2 核心模块

| 模块 | 职责 |
|---|---|
| 认证模块 | 登录、登出、会话/令牌管理 |
| 用户模块 | 用户信息、账号状态 |
| 组织模块 | 公司、部门、团队结构维护 |
| 角色权限模块 | 角色与权限，服务端数据过滤 |
| 日志模块 | 草稿、提交、截止自动处理、状态流转 |
| 点评模块 | 直接上级点评、下级回复、可见性控制 |
| 统计模块 | 提交率、未提交名单、日志数量、趋势、重点事项 |
| 派发任务模块 | 直属下级派发、共享任务内容、接收人独立进度、完成检查邀约与结果 |
| 自建任务模块 | 用户本人创建、查看和编辑的个人任务 |
| 公司重点展示模块 | 管理员维护公司十大重要事项、创始人维护公司十大重要任务，独立于常规任务 |
| 任务呈现模块 | 导图页、个人面板、日历视图、只读数据地图的数据组合与展示 |
| 系统配置模块 | 截止时间等参数 |
| 审计模块 | 管理员操作记录 |

## 5. 核心数据模型

### 5.1 组织与用户

| 表 | 主要字段 |
|---|---|
| companies | 公司 ID、名称（单公司） |
| departments | 部门 ID、名称、公司 ID、部门老总 ID |
| teams | 团队 ID、名称、部门 ID、团队长 ID |
| users | 用户 ID、账号、密码摘要、姓名、角色、部门 ID、团队 ID、状态、创建时间 |

### 5.2 角色与权限

角色采用固定枚举：员工、团队长、部门老总、创始人、系统管理员。权限主要体现为数据可见范围和功能开关：

| 角色 | 日志可见范围 | 点评权限 | 任务能力 | 管理权限 |
|---|---|---|---|---|
| 员工 | 自己 | 被点评/回复 | 任务接收、更新本人进度、邀约检查、自建任务 | 无 |
| 团队长 | 本团队 | 点评直接下级 | 向本团队员工派发、检查；任务接收、自建任务 | 无 |
| 部门老总 | 本部门 | 点评直接下级（团队长） | 向本部门团队长派发、检查；任务接收、自建任务 | 无 |
| 创始人 | 全公司 | 点评直接下级（部门老总） | 向部门老总派发、检查；任务接收、自建任务；维护公司十大重要任务 | 无 |
| 系统管理员 | 全公司（只读） | 无 | 只读公司展示内容；不可查看或操作他人任务 | 用户/组织/角色/权限/配置；维护公司十大重要事项 |

### 5.3 日志与点评

| 表 | 主要字段 |
|---|---|
| work_logs | 日志 ID、作者 ID、日志日期、内容、状态、提交时间、创建/更新时间 |
| log_comments | 评论 ID、日志 ID、评论人 ID、内容、父评论 ID、创建时间 |

日志状态：草稿、已提交。未提交用户不落 work_logs 记录，或通过统计维度区分（建议由「当日无记录且已过截止时间」判定）。

### 5.4 任务与公司展示内容

| 实体 | 主要字段/关系 | 说明 |
|---|---|---|
| `tasks` | ID、派发人、名称、详情、开始日期、截止日期、紧急程度、创建/更新时间 | 一条共享派发任务内容；截止日期不得早于开始日期 |
| `task_assignments` | ID、任务 ID、被派发人、执行状态、当前检查状态、创建/更新时间 | 每个被派发人一条独立记录；任务 ID + 被派发人唯一 |
| `task_reviews` | ID、接收记录 ID、检查结果、意见、检查人、检查时间 | 记录逐接收人的检查邀约/结果历史，不串改其他接收人 |
| `personal_tasks` | ID、所有者、名称、详情、状态、创建/更新时间 | 仅本人可见编辑；无日期、紧急程度或派发检查 |
| `company_matters` | 展示内容、管理员维护信息、更新时间 | 管理员通过 Web 发布/编辑 |
| `company_important_tasks` | 展示内容、创始人维护信息、更新时间 | 创始人通过 Android 发布/编辑 |

公司展示内容不写入常规任务表，不生成接收记录，不进入任务统计、数据地图或日历。

数据关系为：一条 `tasks` 共享任务内容对应多条 `task_assignments` 接收记录（任务 ID + 被派发人唯一），一条接收记录对应多条 `task_reviews` 检查历史；`personal_tasks` 按所有者独立存储，不与 `tasks`/`task_assignments` 建立关联；`company_matters` 与 `company_important_tasks` 为两套独立展示表，仅记录发布者维护信息。

### 5.5 统计与审计

| 表 | 主要字段 |
|---|---|
| system_configs | 配置项、配置值（如截止时间） |
| operation_audits | 操作人、操作类型、对象、时间、结果 |

统计指标可基于 work_logs 实时计算，规模较小时不必预聚合。

## 6. 权限与可见性设计

### 6.1 日志可见规则

服务端在查询日志时按当前用户角色和归属强制拼接过滤条件：

- 员工：author_id = 自己。
- 团队长：author 所在团队 = 自己的团队。
- 部门老总：author 所在部门 = 自己的部门。
- 创始人：无过滤，全公司。
- 系统管理员：无过滤（只读）。

### 6.2 点评可见规则

点评对话仅对「作者 + 作者的直接上级」开放。服务端查询评论时：

- 允许：评论作者、日志作者、日志作者的直接上级。
- 拒绝：同团队/同部门其他成员，以及更上级（如部门老总看团队长点评员工）。

### 6.3 管理员权限

- 可读：所有用户、组织、日志、统计。
- 可写：用户、组织、角色、权限、系统配置。
- 不可写：日志内容（不可修改或删除）。

### 6.4 任务权限与可见性

- 常规任务只能沿直接组织关系向下派发：创始人→部门老总、部门老总→团队长、团队长→员工，不允许跨级或跨组织。
- 派发人负责任务内容和逐接收人检查；被派发人只可更新自己的执行进度。每个接收人的状态和检查记录彼此独立。
- 自建任务仅创建者本人可见、可编辑。管理员的全公司日志只读权限不扩展为查看他人任务的权限。
- 公司十大重要事项由管理员在 Web 端维护，公司十大重要任务由创始人在 Android 端维护，其他用户只读。
- 数据地图仅读取当前用户收到的派发任务和本人自建任务；不显示派发给他人的任务或公司展示内容。

## 7. 关键业务流程

### 7.1 日志状态流转

```text
新建日志（内容非空）
      │
      ▼
   草稿 ──编辑──▶ 草稿
      │
      ├── 正式提交 ──▶ 已提交（不可修改）
      │
      └── 到截止时间（有草稿）──▶ 自动作为当日日志（已提交）

截止时间（无草稿）──▶ 未提交（不可补交）
```

### 7.2 点评流程

```text
员工提交日志
      │
      ▼
团队长（直接上级）发起点评
      │
      ▼
员工回复 → 形成对话
      │
      └─ 仅员工与团队长可见
```

### 7.3 登录流程

```text
账号密码 → 服务端校验 → 返回令牌 → 客户端按角色加载对应界面
```

### 7.4 派发任务与逐人检查

```text
派发人创建任务内容 + 一个或多个直接下级
       │ 服务端校验组织关系、字段和日期
       ▼
共享任务内容 ─── 逐接收人独立进度记录
                       │ 被派发人完成并邀请检查
                       ▼
                     待检查
                   ／       ＼
             检查通过       退回修改
                                │
                         本人继续进行中
                         完成后再次邀请
```

每名接收人独立经历未开始、进行中、已完成、待检查、检查通过或退回修改；退回只将该接收人的执行状态恢复为进行中。检查不依赖通知推送。

### 7.5 四个页面数据来源

- 导图页 2×2：公司十大重要事项、公司十大重要任务、个人十大工作任务（即自建任务）、个人日志。公司内容只有对应发布者可编辑；个人任务和允许编辑的日志草稿支持原地编辑，不改变既有日志截止与提交规则。
- 个人面板：日志、个人任务、任务分发、任务接收；分发仅对有权限的角色开放。
- 视图页：默认手机当前月，可切换月/周/日；接收的派发任务日期范围标绿，日志日期标红，同日任务优先绿色；自建任务不入日历。
- 数据地图：只读聚合本人收到的派发任务和自建任务；自建任务没有日期、紧急程度时留空，内容/状态必须回到来源页面修改。

## 8. 接口设计概要

| 分组 | 主要接口 |
|---|---|
| 认证 | 登录、登出、刷新令牌 |
| 用户 | 创建、查询、编辑、停用/启用 |
| 组织 | 公司/部门/团队的增删改查 |
| 日志 | 新建、保存草稿、提交、查询详情、列表 |
| 点评 | 发起点评、回复、查询对话 |
| 统计 | 个人/团队/部门/公司统计 |
| 配置 | 读取/修改系统参数 |
| 审计 | 查询操作记录 |
| 任务分发 | 直接下级选择、任务创建/编辑、派发任务列表 |
| 任务接收与检查 | 本人接收列表、执行状态、完成邀约、派发人检查通过/退回 |
| 自建任务 | 本人任务新增、查询、编辑 |
| 公司展示内容 | 管理员维护事项、创始人维护重要任务、其他用户只读查询 |
| 任务呈现 | 日历任务/日志读取、只读数据地图聚合 |

所有接口统一鉴权，并在服务端按第 6 节规则做数据权限过滤。

## 9. 部署架构

```text
┌────────────┐
│   Nginx    │  （反向代理，暂定腾讯云，现阶段本地/容器即可）
└─────┬──────┘
      │
 ┌────┴─────┐        ┌──────────────┐
 │ React Web │        │ Spring Boot   │
 └──────────┘        │ 后端服务       │
                      └──────┬───────┘
                             │
                      ┌──────▼───────┐
                      │ PostgreSQL    │
                      └──────────────┘
```

使用 Docker 容器化，建议以 docker-compose 编排 Web、后端和数据库。本期先实现本地或容器运行，腾讯云与 Nginx 生产部署后置。

## 10. 迭代与分工建议

### 10.1 Sprint 规划

| Sprint | 目标 | 主要交付 |
|---|---|---|
| Sprint 0 | 需求与设计 | 需求文档、顶层设计、日志与任务数据模型、接口契约、OpenSpec 初始化 |
| Sprint 1 | 首条闭环 | 登录 → 新建日志 → 草稿 → 提交 → 落库 |
| Sprint 2 | 核心功能 | 按角色查看日志、点评对话、统计、管理端；任务派发、任务接收、逐接收人进度与检查、自建任务、公司十大重要事项/任务展示与维护 |
| Sprint 3 | 测试与发布 | 截止自动处理、任务状态机与对象鉴权、日历与数据地图、权限校验、非功能测试、部署演示 |
| Final | 验收展示 | 完整系统、测试报告、演示材料 |

### 10.2 五人分工总览

| 成员 | 建议角色 | 主要负责 |
|---|---|---|
| A | 产品/需求 | 需求文档、用户故事、验收标准、原型、Backlog |
| B | Android 端 | Flutter 登录、日志、任务分发/接收、自建任务、导图/视图/个人面板/数据地图 |
| C | Web 端 | React 管理端、用户/组织/角色/权限/配置、只读日志与统计、公司重要事项维护 |
| D | 后端与数据 | Spring Boot、MyBatis、PostgreSQL、日志与任务契约、领域权限和数据模型 |
| E | 测试与工程质量 | 日志/任务测试计划、接口与端到端、权限隔离、非功能验证、Docker/CI |

### 10.3 协作要求

- 全员在 Git 平台使用独立分支，保留可核验提交记录。
- 后端先定接口契约，前端可先用 Mock 数据并行开发。
- 权限规则统一由后端定义，前端只负责展示和路由控制。
- 测试从 Sprint 0 开始介入，每个 Sprint 都执行测试。
- 不以「代码完成」代替「功能验收」，必须提供运行或测试证据。
