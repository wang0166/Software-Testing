# 产品需求文档 —— 智能掌上日志系统（潘多拉 Pandora）

## 1. 文档说明

本文档定义「智能掌上日志系统（潘多拉 Pandora）」的产品需求，作为后续顶层设计、原型、开发、测试和验收的依据。

需求已经与甲方逐项澄清，本版本不再是猜测稿。文中把已经确认的结论放在正文，把允许自由发挥、不影响本期交付的内容单独列为后置项。

## 2. 产品概述

### 2.1 产品定位

Pandora 是一套面向单公司的智能工作日志系统，由 Android 移动端和 Web 管理端组成：

- Android 端：员工、团队长、部门老总、创始人日常填写日志、查看日志与统计、进行点评。
- Web 管理端：仅系统管理员使用，用于用户、组织、角色、权限和系统配置管理，并可只读查看全公司日志与统计。

### 2.2 产品愿景

通过统一、及时、结构化的工作日志采集与统计，帮助员工沉淀工作成果，帮助各级负责人掌握团队/部门进展，帮助公司最高负责人看到全局情况。

### 2.3 要解决的问题

- 日志记录方式不统一，信息分散；
- 负责人难以及时掌握下级工作进展；
- 工作成果缺少持续、结构化的记录；
- 日志只写不看，缺少统计和趋势沉淀；
- 组织层级之间的信息可见边界不清晰。

### 2.4 产品价值

| 用户 | 核心价值 |
|---|---|
| 员工 | 每天快速写一条日志，回看自己的工作记录与提交情况 |
| 团队长 | 查看本团队全部日志，点评直接下级，掌握团队提交情况 |
| 部门老总 | 查看本部门全部日志，点评团队长，掌握部门整体情况 |
| 创始人 | 查看全公司日志与统计，掌握公司整体运转 |
| 系统管理员 | 维护用户、组织、角色、权限和系统配置，只读查看日志与统计 |

## 3. 术语

- 直接上级：员工 → 团队长，团队长 → 部门老总，部门老总 → 创始人。
- 日志：一名用户在某一天写的一条工作记录。
- 草稿：尚未正式提交的日志。
- 提交：日志正式落库，提交后不可修改。
- 未提交：当日没有任何草稿、也没有提交。

## 4. 组织模型与身份约束

### 4.1 组织层级

系统为单公司、单创始人。层级固定为四级：

```text
公司
 └─ 部门（1 至多个）
     └─ 团队/项目组（每个部门下 1 至多个）
         └─ 员工
```

- 一个公司只有一名创始人。
- 一个部门只有一名部门老总。
- 一个团队只有一名团队长，不允许一个团队有多个负责人。

### 4.2 用户角色

| 角色 | 归属 | 日志可见范围 |
|---|---|---|
| 员工 | 属于一个团队 | 只看自己的日志 |
| 团队长 | 属于一个团队 | 看本团队全部日志（含自己） |
| 部门老总 | 属于一个部门，不属于具体团队 | 看本部门所有团队成员的日志（含自己） |
| 创始人 | 公司最高负责人，不属于团队 | 看全公司所有人的日志 |
| 系统管理员 | 独立账号，不属于任何部门/团队 | 可只读查看全公司日志与统计 |

### 4.3 身份约束

- 每个用户只有一种身份/角色，不能兼任（例如不能同时是员工和团队长）。
- 「一个用户只能属于一个团队」只对员工和团队长生效。
- 部门老总属于一个部门，但不属于任何团队。
- 创始人和系统管理员不属于任何部门或团队。
- 创始人、部门老总、团队长、员工都要每天写一条工作日志；系统管理员不写日志。

## 5. 核心业务规则

### 5.1 日志规则

1. 每人每天最多写一条日志。
2. 日志内容为自由文本，可以像清单一样一行一行写；没有固定字段、没有必填字段，但内容不能为空。
3. 日志日期由系统自动取当天，不允许选择其他日期，也不允许补交历史日期。
4. 提交前可以反复编辑、保存草稿。
5. 正式提交后不能修改。
6. 每日 22:00 为提交截止时间（默认值，系统管理员可在 Web 端配置）。
7. 到 22:00 时：存在草稿的，草稿自动作为当日日志；不存在草稿的，记为未提交。
8. 超过 22:00 后不可再提交或补交。

### 5.2 点评规则

1. 只有日志作者的直接上级可以发起点评。
2. 下级可以回复上级的点评，形成对话。
3. 点评对话只对「作者 + 作者的直接上级」可见、可参与。
4. 同部门、同团队的其他成员看不到点评；更上级（如部门老总看团队长点评员工、创始人看部门老总点评团队长）也看不到、不能参与。
5. 创始人没有直接上级，因此创始人的日志无人可以点评。

### 5.3 数据可见性

- 员工：只能看自己的日志，不能看同团队其他成员或其他部门的日志。
- 团队长：只能看本团队的日志，不能跨组查看。
- 部门老总：只能看本部门的日志，不能跨部门查看。
- 创始人：可以看全公司所有人的日志。
- 系统管理员：可以只读查看全公司日志和统计，但不能修改或删除日志。

## 6. 功能需求

### 6.1 账号与登录

- 系统管理员在 Web 端创建所有账号（员工、团队长、部门老总、创始人、管理员），不支持自助注册。
- 用户使用账号密码登录 Android 端。
- 用户可退出登录。
- 管理员可停用或启用账号。

### 6.2 日志填报

- 登录后进入「我的日志」。
- 新建当日日志，内容为自由文本，非空。
- 支持保存草稿、反复编辑。
- 支持正式提交，提交后不可修改。
- 日期自动取当天，不可改。
- 每人每天仅一条。
- 22:00 自动处理草稿/未提交，截止后不可补交。

### 6.3 日志查看

- 按角色展示对应可见范围的日志列表与详情。
- 系统在服务端按角色和归属强制过滤，禁止越权访问。

### 6.4 点评对话

- 直接上级对自己下级的日志发起点评。
- 下级回复，形成对话。
- 点评对话仅作者和直接上级可见、可参与。

### 6.5 统计看板（Android 端）

员工、团队长、部门老总、创始人各自在 Android 端查看自己权限范围内的统计。统计指标由我方设计，建议包含：

- 提交率：已提交（含 22:00 自动提交的草稿）人数 / 应提交人数。
- 未提交名单。
- 日志数量统计（按日/周/月）。
- 工作趋势（近 7/30 天日志量变化）。
- 重点事项：由直接上级人工标记为重要（可选）。

说明：由于日志为自由文本、无「完成情况」字段，原「完成率」指标改为以「提交状态」呈现。

### 6.6 系统管理（Web 端，仅管理员）

- 维护用户：创建、编辑、停用/启用账号，分配角色和归属。
- 维护组织：公司、部门、团队结构。
- 维护角色与权限。
- 维护系统配置：如日志提交截止时间。
- 查看所有用户信息、所有日志和统计（日志只读，不可修改或删除）。

## 8. 关键验收标准

### US-07 新建日志

正常场景：用户登录后新建当日日志，填写自由文本内容，保存成功，日志状态为草稿。

异常/边界：

- 内容为空时不允许保存或提交。
- 日期只能是当天，不能选择未来或过去日期。
- 每人每天只能有一条日志，重复创建被拒绝。

### US-09 提交日志

正常场景：草稿内容非空，用户点击提交后状态变为已提交，提交后不可再编辑。

异常/边界：

- 内容为空时禁止提交。
- 已提交日志不能重复提交。
- 非日志作者不能修改日志。

### US-11 截止自动处理

正常场景：到截止时间，系统把存在草稿的日志自动计为当日已提交日志。

异常/边界：

- 截止时无草稿的用户记为未提交。
- 截止后不可补交。
- 截止时间以管理员在 Web 端配置的值为准。

### US-15/16/17 可见范围

- 员工只能看到自己的日志。
- 团队长只能看到本团队日志。
- 部门老总只能看到本部门日志。
- 创始人可以看到全公司日志。
- 任何越权查询都返回无权限或空结果，且服务端强制过滤。

### US-21 点评隐私

- 点评对话只有作者和作者的直接上级可见、可参与。
- 同团队其他成员、更上级均不可见、不可参与。

### US-27 管理员只读

- 管理员可以在 Web 端查看全公司日志和统计。
- 管理员不能修改或删除任何日志。

## 9. 非功能需求

实训要求至少落实两项。建议落实安全性、性能、易用性和可靠性/隐私四项。

### 9.1 安全性

- 密码不得明文存储。
- 用户只能访问授权范围内的数据，服务端强制校验。
- 关键操作写入审计日志。
- 登录失败达到上限后进行限制。

### 9.2 性能

- 普通页面加载时间不超过 3 秒。
- 日志列表查询响应时间不超过 2 秒。
- 100 条以内日志的统计页面生成时间不超过 3 秒。
- 关键接口成功率不低于 99%。

### 9.3 易用性

- 新用户能够在 3 分钟内完成第一条日志提交。
- 日志填写交互清晰，错误信息说明修复方式。
- 移动端主要操作不超过 3 层页面。
- 常用 Android 分辨率下页面正常显示。

### 9.4 可靠性与隐私

- 保存失败时不得显示虚假成功。
- 网络中断后尽可能保留已输入内容。
- 提交操作避免重复创建。
- 敏感信息不得发送给未经授权的外部服务。

## 10. MVP 范围

### 10.1 MVP 必须包含

1. 账号密码登录、退出登录。
2. 角色与权限控制。
3. 组织管理（公司、部门、团队）。
4. 日志新建、草稿保存、提交。
5. 提交后不可修改、每日一条、日期自动取当天。
6. 截止时间自动处理草稿与未提交。
7. 按角色的日志查看与数据权限隔离。
8. 直接上级点评、下级回复、点评隐私控制。
9. Android 端个人/团队/部门/公司统计看板。
10. Web 管理端：用户、组织、角色、权限、系统配置，以及日志/统计只读查看。
11. 关键业务测试和异常处理。

### 10.2 后置/增强功能

- AI 日志摘要、关键词提取、趋势分析。
- MBTI/职业性格分析。
- 消息通知（本期先不做）。
- 数据导出。
- 离线填写。

说明：Docker、Nginx 属于部署架构，在《顶层设计文档》中说明，不属于「增强功能」。
