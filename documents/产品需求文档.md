# 产品需求文档 —— 智能掌上日志系统（潘多拉 Pandora）

## 1. 文档说明

本文档定义「智能掌上日志系统（潘多拉 Pandora）」的产品需求，作为后续顶层设计、原型、开发、测试和验收的依据。

需求已经与甲方逐项澄清，本版本不再是猜测稿。文中把已经确认的结论放在正文，把允许自由发挥、不影响本期交付的内容单独列为后置项。

## 2. 产品概述

### 2.1 产品定位

Pandora 是一套面向单公司的智能工作日志系统，由 Android 移动端和 Web 管理端组成：

- Android 端：员工、团队长、部门老总、创始人日常填写日志、查看日志与统计、进行点评，并查看个人工作任务、派发或接收任务。
- Web 管理端：仅系统管理员使用，用于用户、组织、角色、权限和系统配置管理，发布公司十大重要事项，并可只读查看全公司日志与统计。

### 2.2 产品愿景

通过统一、及时、结构化的工作日志和任务管理，帮助员工沉淀工作成果、明确任务责任与进度，帮助各级负责人掌握团队/部门进展，帮助公司最高负责人看到全局情况。

### 2.3 要解决的问题

- 日志记录方式不统一，信息分散；
- 负责人难以及时掌握下级工作进展；
- 工作成果缺少持续、结构化的记录；
- 任务派发、负责人、期限与完成检查缺少统一跟踪；
- 日志只写不看，缺少统计和趋势沉淀；
- 组织层级之间的信息可见边界不清晰。

### 2.4 产品价值

| 用户 | 核心价值 |
|---|---|
| 员工 | 每天快速写一条日志，查看自己的工作记录、个人任务和收到的任务 |
| 团队长 | 查看本团队全部日志，点评直接下级，向直接下级派发任务并掌握团队提交情况 |
| 部门老总 | 查看本部门全部日志，点评团队长，向直接下级派发任务并掌握部门整体情况 |
| 创始人 | 查看全公司日志与统计，发布公司十大重要任务，并向直接下级派发任务 |
| 系统管理员 | 使用 Web 管理用户、组织、角色、权限和系统配置，发布公司十大重要事项，只读查看日志与统计 |

## 3. 术语

- 直接上级：员工 → 团队长，团队长 → 部门老总，部门老总 → 创始人。
- 日志：一名用户在某一天写的一条工作记录。
- 草稿：尚未正式提交的日志。
- 提交：日志正式落库，提交后不可修改。
- 未提交：当日没有任何草稿、也没有提交。
- 任务：有明确派发人和一个或多个被派发人的工作事项；每名被派发人分别维护自己的任务状态。
- 自建任务：用户为自己添加和管理的个人任务，不派发给其他人。
- 检查邀约：被派发人完成任务后，邀请派发人检查该被派发人的完成情况。
- 公司十大重要事项/公司十大重要任务：分别由系统管理员/创始人发布的导图页展示内容，不属于常规任务记录，不进入数据地图或日历任务标记。

## 4. 组织模型与身份约束

### 4.1 组织层级

系统为单公司、单创始人。层级固定为四级：

```text
公司
 └─ 部门（1 至多个）
     └─ 团队/项目组（每个部门下 1 至多个）
         └─ 员工
```

- 一个公司只有一名创始人。
- 一个部门只有一名部门老总。
- 一个团队只有一名团队长，不允许一个团队有多个负责人。

### 4.2 用户角色

| 角色 | 归属 | 日志可见范围 |
|---|---|---|
| 员工 | 属于一个团队 | 只看自己的日志 |
| 团队长 | 属于一个团队 | 看本团队全部日志（含自己） |
| 部门老总 | 属于一个部门，不属于具体团队 | 看本部门所有团队成员的日志（含自己） |
| 创始人 | 公司最高负责人，不属于团队 | 看全公司所有人的日志 |
| 系统管理员 | 独立账号，不属于任何部门/团队 | 可只读查看全公司日志与统计 |

### 4.3 身份约束

- 每个用户只有一种身份/角色，不能兼任（例如不能同时是员工和团队长）。
- 「一个用户只能属于一个团队」只对员工和团队长生效。
- 部门老总属于一个部门，但不属于任何团队。
- 创始人和系统管理员不属于任何部门或团队。
- 创始人、部门老总、团队长、员工都要每天写一条工作日志；系统管理员不写日志。

## 5. 核心业务规则

### 5.1 日志规则

1. 每人每天最多写一条日志。
2. 日志内容为自由文本，可以像清单一样一行一行写；没有固定字段、没有必填字段，但内容不能为空。
3. 日志日期由系统自动取当天，不允许选择其他日期，也不允许补交历史日期。
4. 提交前可以反复编辑、保存草稿。
5. 正式提交后不能修改。
6. 每日 22:00 为提交截止时间（默认值，系统管理员可在 Web 端配置）。
7. 到 22:00 时：存在草稿的，草稿自动作为当日日志；不存在草稿的，记为未提交。
8. 超过 22:00 后不可再提交或补交。

### 5.2 任务规则

1. 常规任务由有任务分发权限的用户向自己的直接下级派发：创始人向部门老总派发，部门老总向团队长派发，团队长向员工派发；不得跨越直接上下级关系派发。
2. 一个任务可以关联多个被派发人。任务名称、详情、开始日期、截止日期、紧急程度等任务内容由派发人维护；每名被派发人分别维护自己的进度状态和检查邀约，互不影响。
3. 每名被派发人的执行状态为未开始、进行中、已完成；完成后可进入待检查，由派发人给出检查通过或退回修改的检查结果。被派发人只能更新自己的执行状态，派发人只能给出检查结果，不能代替被派发人更新执行进度。
4. 被派发人完成任务后可以发起检查邀约，任务进入待检查。派发人检查后可标记检查通过，或退回修改；退回后该被派发人的任务状态回到进行中，修改完成后可再次邀请检查。
5. 派发人和被派发人共同负责该任务：派发人负责任务内容与检查，被派发人负责执行并更新自己的进度。任务日常编辑中派发人只能修改任务内容，被派发人只能修改自己的进度状态；派发人的检查操作不属于代改执行进度。
6. 自建任务只属于创建用户本人且仅本人可编辑，不设置开始日期、截止日期或紧急程度；至少包含任务名称、详情和进度状态，状态为未开始、进行中、已完成，不走派发检查流程。
7. 公司十大重要事项由系统管理员通过 Web 管理端发布和编辑；公司十大重要任务由创始人发布和编辑。两类内容是独立展示模块，其他用户只读，不参与常规任务派发、任务统计、数据地图或日历标记。

### 5.3 页面与任务呈现规则

1. 导图页展示 2×2 四个板块：左上公司十大重要事项、右上公司十大重要任务、左下个人十大工作任务、右下个人日志。前两个板块对非发布者只读；个人十大工作任务与用户的自建任务是同一份数据和入口。个人任务可直接在板块中编辑；个人日志可在原日志规则允许编辑时直接编辑草稿，提交后仍不可修改。双击编辑不跳转到其他页面。
2. 视图页默认显示根据手机当前日期确定的当月日历，并可切换月视图、周视图、日视图。周视图显示该周 7 天；日视图以白色背景展示当天的任务和日志。月视图和周视图按日志日期标红，按派发任务的开始日期至截止日期标绿；同一天既有日志又有任务时只标绿。用户自建任务无日期，不进入日历视图。
3. 个人面板由日志、个人十大工作任务、任务分发、任务接收四个功能板块组成，布局依次为左上、右上、左下、右下。任务分发仅对有对应权限的用户开放；任务接收展示派发给当前用户的任务清单。
4. 数据地图仅展示任务清单，包含派发给当前用户的任务和用户自建任务。展示字段包括任务名称、截止日期、紧急程度、个人进度状态等；自建任务没有的日期和紧急程度字段留空。数据地图只读，任务内容需回到任务来源页面修改，状态需在任务接收或个人任务入口更新，并同步反映到数据地图。

### 5.4 点评规则

1. 只有日志作者的直接上级可以发起点评。
2. 下级可以回复上级的点评，形成对话。
3. 点评对话只对「作者 + 作者的直接上级」可见、可参与。
4. 同部门、同团队的其他成员看不到点评；更上级（如部门老总看团队长点评员工、创始人看部门老总点评团队长）也看不到、不能参与。
5. 创始人没有直接上级，因此创始人的日志无人可以点评。

### 5.5 数据可见性

- 员工：只能看自己的日志，不能看同团队其他成员或其他部门的日志。
- 团队长：只能看本团队的日志，不能跨组查看。
- 部门老总：只能看本部门的日志，不能跨部门查看。
- 创始人：可以看全公司所有人的日志。
- 系统管理员：可以只读查看全公司日志和统计，但不能修改或删除日志。
- 任务接收列表只展示派发给当前用户的个人任务；任务分发列表由派发人管理其派发的任务；自建任务仅创建者本人可见和编辑。每个任务接收人的进度和检查过程仅作用于该接收人。

## 6. 功能需求

### 6.1 账号与登录

- 系统管理员在 Web 端创建所有账号（员工、团队长、部门老总、创始人、管理员），不支持自助注册。
- 用户使用账号密码登录 Android 端。
- 用户可退出登录。
- 管理员可停用或启用账号。

### 6.2 日志填报

- 登录后进入「我的日志」。
- 新建当日日志，内容为自由文本，非空。
- 支持保存草稿、反复编辑。
- 支持正式提交，提交后不可修改。
- 日期自动取当天，不可改。
- 每人每天仅一条。
- 22:00 自动处理草稿/未提交，截止后不可补交。

### 6.3 日志查看

- 按角色展示对应可见范围的日志列表与详情。
- 系统在服务端按角色和归属强制过滤，禁止越权访问。

### 6.4 点评对话

- 直接上级对自己下级的日志发起点评。
- 下级回复，形成对话。
- 点评对话仅作者和直接上级可见、可参与。

### 6.5 统计看板（Android 端）

员工、团队长、部门老总、创始人各自在 Android 端查看自己权限范围内的统计。统计指标由我方设计，建议包含：

- 提交率：已提交（含 22:00 自动提交的草稿）人数 / 应提交人数。
- 未提交名单。
- 日志数量统计（按日/周/月）。
- 工作趋势（近 7/30 天日志量变化）。
- 重点事项：由直接上级人工标记为重要（可选）。

说明：由于日志为自由文本、无「完成情况」字段，原「完成率」指标改为以「提交状态」呈现。

### 6.6 系统管理（Web 端，仅管理员）

- 维护用户：创建、编辑、停用/启用账号，分配角色和归属。
- 维护组织：公司、部门、团队结构。
- 维护角色与权限。
- 维护系统配置：如日志提交截止时间。
- 查看所有用户信息、所有日志和统计（日志只读，不可修改或删除）。
- 发布和编辑公司十大重要事项；该展示内容不生成常规任务记录。

### 6.7 任务管理（Android 端）

#### 6.7.1 公司十大重要任务展示

- 创始人在 Android 端发布和编辑公司十大重要任务展示内容。
- 其他用户只读查看。该模块与常规任务分发、任务接收、数据地图和日历相互独立，不形成任务记录。

#### 6.7.2 任务分发

- 创始人、部门老总、团队长按组织层级向直接下级派发任务；不得跨级或跨组织派发。
- 任务表单包含任务名称、详情、开始日期、截止日期、紧急程度和一个或多个被派发人。紧急程度至少区分“紧急”和“不紧急”。
- 派发人可修改其派发任务的内容，但不能代替接收人修改个人进度状态。
- 派发任务后，各被派发人分别获得独立任务进度，不共享进度状态。

#### 6.7.3 任务接收与检查

- 当前用户可查看派发给自己的任务清单，包含名称、详情、开始/截止日期、紧急程度和自己的进度状态。
- 被派发人可更新自己的状态：未开始、进行中、已完成；完成后可邀请派发人检查，状态变为待检查。
- 派发人可以对每名被派发人分别进行检查，并将其状态改为检查通过或退回修改。退回修改后，被派发人可继续更新为进行中并再次邀请检查。
- 一个任务的多个接收人分别更新进度、分别发起检查邀约、分别接受检查结果。

#### 6.7.4 个人十大工作任务（自建任务）

- 用户通过个人十大工作任务入口查看、新增和编辑自己的任务；个人十大工作任务与导图页同名板块同步。
- 自建任务只属于创建者本人，其他用户不能查看或编辑。
- 自建任务包含名称、详情和进度状态；不要求开始日期、截止日期或紧急程度，没有日期的自建任务不在日历中标记。
- 用户可在个人面板或导图页的个人任务板块修改自己的自建任务。

### 6.8 主要业务页面

#### 6.8.1 导图页

- 以 2×2 板块呈现公司十大重要事项、公司十大重要任务、个人十大工作任务和个人日志。
- 公司展示内容只允许对应发布者（管理员或创始人）编辑，其他用户只读。
- 个人十大工作任务支持板块内直接编辑；个人日志仅可在日志规则允许编辑时（草稿、截止前）直接编辑，提交后不可修改。双击进入编辑态，不跳转至其他功能页面。
- 原型中的“重要且紧急”等四象限标签不作为板块名称，原型仅供布局参考；个人任务和日志板块以可编辑文本区域呈现，不因双击而跳转。

#### 6.8.2 视图页

- 根据手机当前日期自动定位当月，默认月视图；用户可以切换月、周、日视图。
- 月视图展示当月日历，周视图展示所选周的 7 天，日视图展示当天日志和任务。
- 派发任务的有效日期范围在月/周视图中标绿，日志日期标红；任务和日志同日时以任务绿色为准。
- 日期范围包含开始日和截止日，截止日期不得早于开始日期；视图页左上角提供日、周、月视图选择按钮。
- 日历的任务颜色仅表示日期占用，不额外表达任务进度或紧急程度。

#### 6.8.3 个人面板

- 展示日志、个人十大工作任务、任务分发和任务接收四个板块。
- 日志继续使用本文件既有日志规则；个人十大工作任务管理自建任务；任务分发用于创建和维护向直接下级派发的任务；任务接收用于查看本人被派发任务并更新本人进度。

#### 6.8.4 数据地图

- 只提供任务清单展示，不提供任务编辑。
- 数据来源为派发给当前用户的任务及当前用户自建任务；公司十大重要事项和公司十大重要任务不纳入数据地图。
- 清单展示任务名称、截止日期、紧急程度、个人进度状态等信息。自建任务没有截止日期和紧急程度时相应字段留空。
- 数据地图随任务来源页面的任务内容或状态变更同步更新。

## 8. 关键验收标准

### US-07 新建日志

正常场景：用户登录后新建当日日志，填写自由文本内容，保存成功，日志状态为草稿。

异常/边界：

- 内容为空时不允许保存或提交。
- 日期只能是当天，不能选择未来或过去日期。
- 每人每天只能有一条日志，重复创建被拒绝。

### US-09 提交日志

正常场景：草稿内容非空，用户点击提交后状态变为已提交，提交后不可再编辑。

异常/边界：

- 内容为空时禁止提交。
- 已提交日志不能重复提交。
- 非日志作者不能修改日志。

### US-11 截止自动处理

正常场景：到截止时间，系统把存在草稿的日志自动计为当日已提交日志。

异常/边界：

- 截止时无草稿的用户记为未提交。
- 截止后不可补交。
- 截止时间以管理员在 Web 端配置的值为准。

### US-15/16/17 可见范围

- 员工只能看到自己的日志。
- 团队长只能看到本团队日志。
- 部门老总只能看到本部门日志。
- 创始人可以看到全公司日志。
- 任何越权查询都返回无权限或空结果，且服务端强制过滤。

### US-21 点评隐私

- 点评对话只有作者和作者的直接上级可见、可参与。
- 同团队其他成员、更上级均不可见、不可参与。

### US-27 管理员只读

- 管理员可以在 Web 端查看全公司日志和统计。
- 管理员不能修改或删除任何日志。

### US-32/33/34/35 任务派发、进度和检查

- 任务只能沿创始人 → 部门老总 → 团队长 → 员工的直接上下级关系向下派发；不允许跨级派发。
- 同一任务可关联多个被派发人，每人具有彼此独立的进度和检查状态。
- 派发人可编辑任务内容；被派发人只能编辑自己的进度状态。
- 状态流转支持未开始、进行中、已完成、待检查、检查通过、退回修改；退回后回到进行中。
- 每名被派发人完成后均可分别邀请派发人检查；一个人的检查结果不改变其他接收人的状态。

### US-36/37 自建任务和数据地图

- 自建任务仅创建者本人可见和编辑，至少包含名称、详情和进度状态。
- 自建任务不要求开始日期、截止日期或紧急程度，不进入日历视图。
- 数据地图只读展示派发给当前用户的任务和本人自建任务；自建任务缺少日期和紧急程度时相应列留空。
- 在任务来源页面更新内容或状态后，数据地图同步显示最新信息；数据地图本身不能修改任务。

### US-38/41 页面验收

- 导图页显示四个指定板块；公司板块只允许对应发布者编辑，个人任务和允许编辑的日志草稿可在板块内直接编辑，不发生页面跳转；已提交日志不可修改。
- 个人面板显示日志、个人十大工作任务、任务分发、任务接收四个功能。

### US-39/40 日历视图验收

- 默认打开手机当前月份；月、周、日视图可切换，周视图为 7 天，日视图为白色背景的当日任务和日志列表。
- 有开始日期和截止日期的派发任务在月/周视图覆盖范围内标绿，日志日期标红；同日同时存在时仅标绿。
- 自建任务不进入日历，日历颜色不编码任务进度或紧急程度。

## 9. 非功能需求

实训要求至少落实两项。建议落实安全性、性能、易用性和可靠性/隐私四项。

### 9.1 安全性

- 密码不得明文存储。
- 用户只能访问授权范围内的数据，服务端强制校验。
- 关键操作写入审计日志。
- 登录失败达到上限后进行限制。

### 9.2 性能

- 普通页面加载时间不超过 3 秒。
- 日志列表查询响应时间不超过 2 秒。
- 100 条以内日志的统计页面生成时间不超过 3 秒。
- 关键接口成功率不低于 99%。

### 9.3 易用性

- 新用户能够在 3 分钟内完成第一条日志提交。
- 日志填写交互清晰，错误信息说明修复方式。
- 移动端主要操作不超过 3 层页面。
- 常用 Android 分辨率下页面正常显示。

### 9.4 可靠性与隐私

- 保存失败时不得显示虚假成功。
- 网络中断后尽可能保留已输入内容。
- 提交操作避免重复创建。
- 敏感信息不得发送给未经授权的外部服务。

## 10. MVP 范围

1. 账号密码登录、退出登录。
