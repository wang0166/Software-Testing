# 潘多拉 Pandora · V1.3.0 企业商务界面整改

> 基于已交付的 V1.2.0 Flutter 工程，并合并后续「任务/AI 地图联调修复」和「日志 setState 异步错误修复」文件。仅用于当前移动端开发分支，未经 Android 真机编译和后端集成验收。

## 一、已实现的 Flutter 改动

| 页面 | V1.3 行为 |
|---|---|
| 导图 | **仅保留四大信息面板**：公司10大重要事项展示、公司10大任务派发、个人10大信息展示、日志展示；在面板内直接列出最多 10 条信息，不需要进入详情才能看到内容。公司/日志数据来自现有服务端接口，**不注入伪造的线上数据**。 |
| 视图 | 默认打开日历，保留年月日点选及月/周/日/甘特图。另有「任务清单」「下属动态」「统计看板」。 |
| 任务清单 | 不再分“收到/派发”两栏。主列表只展示收到任务的**紧凑标题、类型、状态**，详情点开看。右下角加号进入派发申请页面。 |
| 派发申请 | 员工也能申请给上级派任务；成员候选由全公司接口加载；任务可选类型标签与颜色，开始/截止精确到分钟。提交时走待审核新接口，**未经批准绝不直接派发**。 |
| 下属动态 | 汇总授权组织下属收到的所有任务，**不限于当前管理者亲自派发的任务**，需新后端汇总接口。 |
| 日志 | 最近三自然日日期选择、作者重新编辑入口、草稿/提交/已提交修改、上级点评和下级回复；后端必须同步放宽规则。 |
| 头像 | 增加拍照来源，保留相册；目前本机存储，跨设备头像仍需服务端接口。 |
| 视觉 | 冷灰背景、深海军蓝信息栏、商务青色强调、大面积高对比数据区域、直角化表格与克制的图标。 |

## 二、与《智能掌上日志系统（潘多拉 Pandora）》PDF V1.0 的差异

PDF 第 2-3 页定义 Flutter Android / Spring Boot / PostgreSQL、组织层级、角色隔离。PDF 第 7 页明确：**日志只能写当天、每日一条、22:00 截止、提交后不可修改**；PDF 第 9-10 页要求**仅直属上级点评、仅作者回复**。本次**按产品负责人的最新明确变更**改成“最近三天可填可改”，保留一人一天一条、组织权限和点评权限；旧 PDF 规则不再适用，需由团队更新 PRD、接口、数据库测试。

“跨部门/跨层级派发、员工向上级申请、管理员审核、任务分类标签、下属完整工作动态”属于**新增业务需求**，并非 PDF V1.0 已承诺的功能。请后端同学先确认服务端审批流程，再合入 main。

## 三、需要后端实现或变更的接口（**提议契约，不代表现有后端已实现**）

### 1. 查询全公司可选成员

`GET /api/tasks/recipients/all?page=1&size=50`

返回沿用统一 `{code:0,message:'',data:{items:[{id,username,realName,role,departmentId,teamId}],total:180}}`。仅展示当前账号按业务可申请的用户；服务端仍须控制可见信息与可选对象，禁止客户端自定权限范围。

### 2. 创建任务派发审核申请

`POST /api/tasks/dispatch-requests`

请求示例：

```json
{
  "name": "跨部门需求评审",
  "details": "请审核设计方案",
  "startDate": "2026-11-01T09:30:00",
  "deadline": "2026-11-02T18:00:00",
  "urgency": "NOT_URGENT",
  "taskType": "PRODUCT",
  "assigneeIds": [11, 21]
}
```

响应示例：`{ "code":0, "message":"ok", "data": {"id":312,"status":"PENDING"} }`。后端必须写入派发申请表、审批操作审计；审批通过才建立具体 `tasks` 与 assignment 记录，**审批前不能出现在接收任务列表**。员工也可申请派给上级，但需服务端审批。拒绝、过期、重复提交、撤回、审批人权限、幂等键均需后端决定；不能用前端本地标记冒充审批成功。

### 3. 下属所有任务动态

`GET /api/tasks/subordinates/overview?page=1&size=50`

`data.items` 示例：

```json
[
  {
    "userId": 11,
    "name": "演示成员",
    "departmentName": "产品研发部",
    "total": 3,
    "inProgress": 2,
    "completed": 1,
    "tasks": [
      {"assignmentId": 901, "name": "客户端联调", "executionStatus": "IN_PROGRESS", "taskType": "DEVELOPMENT", "deadline": "2026-11-03T18:00:00"}
    ]
  }
]
```

后端需根据角色计算实际的全部下属（包括间接下属，是否跨部门由组织关系决定），从所有发送者的派发记录汇总该下属**已生效**的任务；不得直接暴露未授权的个人任务、审批信息、日志点评。

### 4. 三天日志日期与编辑

沿用 `GET /api/logs?date=YYYY-MM-DD`、`POST /api/logs`、`PUT /api/logs/{id}`、`POST /api/logs/{id}/submit`，写入/更新请求体附带 `logDate`。后端必须校验（亚洲/上海业务日）日期为当天及前两天、每人每天仅一条，并允许作者改动已提交内容。建议增加 `updated_at`、`updated_by` 和编辑审计事件，不覆盖提交历史；保留直接上级点评隔离、回复关系。

如果旧后端不接受 `logDate`，或提交后禁止 `PUT`，真实模式将显示**服务端拒绝**，不应误认为 Flutter 已完成后端改造。

### 5. 任务类型

接收任务查询 `GET /api/tasks/received` 等返回 `taskType` 字段，候选 `GENERAL/DEVELOPMENT/PRODUCT/TESTING/OPERATION/SALES/ADMINISTRATIVE`；后端应在派发申请审核通过后把类型传递至任务记录。前端未收到时显示“综合”。颜色仅视觉区分，不能替代紧急优先级。

## 四、建议验收场景

1. `flutter analyze`、`flutter test`、真实 Android 构建通过。
2. 导图：首页严格仅四面板，四面板各显示数据；账号不具权限时显示暂无数据而不伪造。
3. 视图初始必为日历，点击年月直接选择日期，任务列表和甘特图正常。
4. 任务：只展示收到任务标题、类型、状态，右下角加号可创建申请；员工向部门老总申请派发返回 PENDING，管理员批准后才变为收到任务。
5. 直属上级查看**其他人向其下属派发的任务**；普通员工不能访问下属汇总。
6. 日志：当天/昨天/前天均可创建或修改；第 4 天不可编辑；一人同一天不可重复创建；作者回复直属上级点评；其他人无权阅读点评私聊。
7. 个人头像从相册与相机均可选取；授权被拒时有可理解的错误提示。
8. 使用 `PANDORA_DEMO=false` 测试真机真实后端；禁把演示模式通过当作真实后端通过。
